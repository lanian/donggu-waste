# 휴대폰 앱 v0.10 — 새 기록 종류·목록 필드·외부 서비스 (PC 반영용 규격)

> v0.10.1 추가: 길안내 기본 켬(앱 4종), 주소 검색(행정안전부 도로명주소 API), 반입지 좌표 — 2.5, 3장 `LOCATION_FIX`, 5.1, **8장(외부 서비스)** 참고.

대상: PC 결과 가져오기(`pc/dgpc/service.py import_result`) 담당. 휴대폰 앱 v0.10.0(`web/`)이 결과 파일(`dg.result/1`)에 새로 넣는 기록과, 목록 묶음(`dg.daylist/2`)에 새로 받을 수 있는 필드를 정리합니다.

## 0. 결론 요약

- 결과 파일 형식(`dg.result/1`)·봉투·서명은 **바뀌지 않았습니다.** 기록(`events[]`)의 `kind`가 7개 늘고, 기존 기록 본문에 선택 필드가 몇 개 붙습니다.
- 현재 PC 코드(`import_result`)는 모르는 `kind`를 `result_event`에 `APPLIED`로 저장하고 `derive()`에서는 무시합니다(읽어서 확인함). 그래서 **지금 PC로도 가져오기는 실패하지 않습니다.** 아래 표의 "PC 권장 처리"는 화면에 보여 주려면 할 일입니다.
- 주의: `request_id`가 빈 기록 중 `UNLOAD`가 아닌 것은 지금 PC에서 "PC에 없는 접수" 충돌이 됩니다. 그래서 휴대폰은 **새 팀 단위 기록을 만들지 않습니다**(작업자 교대도 기록이 아니라 각 기록 본문의 `worker`로만 남김).
- 주의: 취소된 접수의 기록은 지금 PC에서 `CONTACT`·`DIAL_INTENT`·`PHOTO_META`만 충돌에서 빠집니다. `ARRIVE`·`SMS_INTENT`·`NAV_INTENT`·`STICKER_CHECK`·`FEE_NOTICE`는 취소 건이면 충돌함으로 갑니다. 충돌 예외 목록에 `ARRIVE`, `SMS_INTENT`, `NAV_INTENT`를 더하는 것을 권장합니다.
- 목록 묶음: 지점에 선택 키 `"d"`(행정동 이름) 추가. **형식 번호는 그대로 `dg.daylist/2`.** `pc/dgproto.py`의 `compact_daylist`/`expand_daylist`에 이미 반영했습니다(지점 dict에 `dong`이 있으면 실림, 없으면 생략).

## 1. 모든 기록 공통

결과 파일의 기록 한 건(기존과 같음):

```json
{ "event_id": "uuid", "seq": 57, "request_id": "uuid", "assign_ver": 2, "base_req_ver": 1,
  "kind": "ARRIVE", "body": { ... }, "device_ts": "2026-11-03T01:05:12.345Z" }
```

### 새 공통 본문 필드 `worker` (선택)

설정에서 작업자 이름을 정해 두면 **모든 기록**(기존 종류 포함, `UNLOAD` 포함)의 `body.worker`에 지금 작업자의 짧은 이름(최대 10자, 예: `"김수거"`)이 들어갑니다. 작업자를 정하지 않았으면 필드가 없습니다. 교대(작업자 바꾸기)는 PIN 없이 이름만 바뀌며 따로 기록하지 않습니다.

PC 권장 처리: 접수 상세의 현장 기록 목록에 작업자 열로 표시. 주민 정보가 아니므로 결과 파일에 들어가는 것이 원칙(이름·연락처·주소 미포함)과 충돌하지 않습니다. 변경 이력(audit)에는 넣지 않아도 됩니다.

## 2. 새 기록 종류 (`kind`)

| kind | 언제 | 진행 상태에 셈 | PC 권장 처리 |
| --- | --- | --- | --- |
| `ARRIVE` | 상세 화면 [도착] | 예 (방문 전 → 처리 중) | 도착 시각·위치 오차 표시. 위치는 접수 좌표를 바꾸지 않음 |
| `STICKER_CHECK` | 품목별 스티커·신고필증 확인 | 예 | 품목 행 옆에 확인/없음/번호 불일치 표시 |
| `FEE_NOTICE` | 현장 금액이 접수 때보다 늘었을 때 고지 | 예 | 수납 기록 화면에 "추가 금액 안내: 동의/안내함/거부" 표시 |
| `SMS_INTENT` | [문자]로 문자 앱 열기 | **아니오** | 연락 이력에 "문자 안내(종류)" 표시 |
| `NAV_INTENT` | [길안내]·[다음 길안내]로 지도 앱 열기 (v0.10.1부터 항상 켬) | **아니오** | 표시만(선택) |

"진행 상태에 셈"은 휴대폰 `fees.js deriveStop`의 `progress` 계산(`NON_PROGRESS` 목록)입니다. PC `derive()`의 `has_field_records`는 지금 `FIELD_ITEM_ADD`·`ITEM_RESULT`·`ATTEMPT`만 세므로 그대로 두어도 상태가 잘못 바뀌지 않습니다.

### 2.1 `ARRIVE`

```json
{ "lat": 35.146213, "lon": 126.923301, "acc": 12, "worker": "김수거" }
```

- 위치 권한이 없거나 설정 "도착·사진에 휴대폰 위치 남기기"를 끈 경우 본문은 `{}`(또는 `worker`만).
- `lat`/`lon`: 소수 6자리, `acc`: 미터(정수). 휴대폰 GPS 값이며 배출 위치가 아님 → `LOCATION_FIX`처럼 접수 좌표를 바꾸면 안 됩니다.
- 시각은 기록의 `device_ts`.
- 같은 지점에서 여러 번 누를 수 있음(마지막 것이 현재 값).

### 2.2 `STICKER_CHECK`

```json
{ "line_id": "uuid", "result": "MISMATCH", "number": "2611-0042", "decision": "LEAVE", "worker": "김수거" }
```

- `result`: `OK`(확인) | `MISSING`(없음) | `MISMATCH`(번호 불일치)
- `number`: 불일치일 때 붙어 있던 번호(선택, 최대 30자). 주민 정보 아님.
- `decision`: `MISSING`/`MISMATCH`일 때만. `COLLECT`(그래도 수거) | `LEAVE`(미수거)
- `LEAVE`이면 바로 뒤에 같은 `line_id`의 `ITEM_RESULT`(`qty_collected: 0`, `reason: "NO_STICKER"`)가 따로 옵니다. 수량 계산은 기존 `ITEM_RESULT` 규칙 그대로.
- `line_id`는 접수 품목 또는 현장 추가 품목(`FIELD_ITEM_ADD`)의 행 ID.

### 2.3 `FEE_NOTICE`

```json
{ "received": 17000, "total": 26000, "extra": 9000, "pending": 1, "response": "AGREED", "worker": "이수거" }
```

- `received`: 접수 당시 금액(확정 단가 행 합), `total`: 현장 확인 수량 기준 확인된 소계, `extra = total − received`(> 0일 때만 기록), `pending`: 금액 확인 대기 행 수(소계에서 빠짐).
- `response`: `AGREED`(동의) | `NOTIFIED`(주민에게 안내함, 답 없음) | `REFUSED`(거부 — 해당 품목 미수거)
- `REFUSED`이면 본문에 `"lines": ["line_id", ...]`가 붙고, 그 앞에 각 행의 `ITEM_RESULT`(`reason: "FEE_REFUSED"`)가 옵니다. 현장 추가 품목은 `qty_collected: 0`, 접수 품목은 접수 수량을 넘는 만큼만 미수거.
- 휴대폰은 결과(수거 완료·일부 수거)를 저장하기 전에, 같은 금액 이상으로 고지한 기록이 없으면 이 창을 띄웁니다. 금액 자체(수수료 계산 규칙)는 바뀌지 않습니다 — 기록일 뿐 수납 완료가 아닙니다.

### 2.4 `SMS_INTENT`

```json
{ "template": "SOON", "worker": "김수거" }
```

- `template`: `SOON`(곧 도착) | `ABSENT`(부재 안내) | `REVISIT`(재방문 안내). 문구 **내용과 번호는 기록하지 않습니다.**
- 문자는 휴대폰 문자 앱이 보내며 앱은 보냈는지 알 수 없습니다(문자 앱을 연 기록).

### 2.5 `NAV_INTENT`

```json
{ "app": "kakao", "worker": "김수거" }
```

- `app`(v0.10.1): `kakao`(카카오맵) | `tmap`(T맵) | `naver`(네이버지도) | `geo`(기본 지도 앱, Android `geo:`) | `apple-maps`(기본 지도 앱, iOS `maps://`). 설정 "길안내 앱"에서 고른 앱(기본 카카오맵). v0.10.0이 만든 기록은 `geo`·`apple-maps`만 있습니다.
- 지도 앱에는 목적지 좌표와 표시 이름 `"N번 수거지"`(N = 방문 순번)만 넘깁니다. 이름·연락처·주소·접수번호는 넘기지 않습니다(8.2).
- 앱이 없어 웹 지도·기본 지도 앱으로 넘어간 경우도 기록은 한 건(처음 고른 앱 이름)입니다. 실제로 안내를 받았는지는 알 수 없습니다.
- 결과 저장 뒤 아래 고정 영역의 **[다음 길안내]**는 다음 미완료 지점을 열며, 그 기록은 **다음 지점의 `request_id`**로 남습니다.
- **반입지 길안내는 기록하지 않습니다**(접수가 없는 팀 기록은 PC에서 "PC에 없는 접수" 충돌이 되므로 — 0장 주의 참고).

## 3. 기존 기록 본문에 붙는 선택 필드

| kind | 새 필드 | 뜻 |
| --- | --- | --- |
| `PHOTO_META` | `taken_at` (ISO) | 사진을 받은 시각(촬영 직후). 기존 필드 `photo_id, phase, sha256, bytes, line_id` 그대로 |
| `PHOTO_META` | `file_ts` (ISO 또는 null) | 카메라가 준 파일 시각 |
| `PHOTO_META` | `lat`, `lon`, `acc` (선택) | 위치 권한이 이미 허용된 경우만(촬영 때 권한 창을 띄우지 않음). 사진 바이트에는 EXIF 위치가 없음(다시 그려 저장) |
| `ATTEMPT` | `no_photo_reason` (선택) | 부재·배출 안 됨으로 `NOT_COLLECTED`를 저장할 때 사진이 없으면 필수: `DARK`(어두움) · `REFUSED`(주민 촬영 거부) · `CAMERA`(카메라 고장) · `OTHER` |
| `ITEM_RESULT` | `reason` 새 값 | `NO_STICKER`(스티커·필증 없음·불일치), `FEE_REFUSED`(추가 금액 거부). 기존 값 `NOT_PUT_OUT, DIFFERENT, CANNOT_LOAD, POSTPONED, OTHER` 그대로 |
| `LOCATION_FIX` | `source: "GPS"`, `acc` (선택) | 지도 조각을 못 받아 [지금 내 위치로 이동]으로 휴대폰 위치를 저장한 경우. 지도로 맞춘 경우는 기존처럼 `source: "MANUAL"` |
| `LOCATION_FIX` | `source: "ADDR"` (v0.10.1) | 위치 지정 화면에서 주소 검색 결과(건물 출입구 좌표)를 그대로 저장한 경우. PC `geo_source`의 `ADDR`과 같은 뜻. 검색 뒤 지도를 움직여 맞추면 `MANUAL` |
| (모두) | `worker` | 1장 참고 |
| (지운 기록) | `pii_purged: true` | 4장 참고 — 휴대폰 안에서만 생김. 보관 종료 확인 뒤에 지우므로 결과 파일로는 보통 나가지 않음 |

PC 권장 처리: 사유 코드 표(`NO_STICKER`, `FEE_REFUSED`)를 PC 화면 사유 이름표에 더하기. "부재 증거" 확인: `ATTEMPT.outcome = NOT_COLLECTED` 이면서 그 접수의 `PHOTO_META`가 없으면 `no_photo_reason`이 있어야 정상.

## 4. 휴대폰 쪽 개인정보 지우기 (PC가 할 일 없음, 참고)

- PC 연결 방식: [결과 보내기]에 **보관 종료 확인 코드**를 넣으면, 그 목록에서 결과가 끝난(`DONE`·`PARTIAL`·`NOT_COLLECTED`) 지점 중 기록이 모두 PC에 반영된 곳의 이름·연락처·주소·상세 위치·메모·좌표를 휴대폰에서 지웁니다(카드에 "개인정보 정리됨"). 수량·결과·사진 기록은 사진 회수까지 남깁니다. 그 지점의 기록에서 메모 글(`FIELD_MEMO.text`)·좌표(`lat/lon/acc`)도 지웁니다.
- 새 날짜 목록을 받으면(이전 결과가 모두 확인된 경우만 받을 수 있음 — 기존 규칙) 이전 목록은 새 목록으로 바뀌고, 이전 날짜 기록의 메모 글·좌표도 지웁니다.
- 같은 날 새 갱신본을 받아도 이미 지운 지점은 지운 채로 둡니다(PC가 다시 보내도 휴대폰에 다시 두지 않음). PC가 재방문을 위해 다시 보낸 경우 휴대폰에서는 접수번호로만 보입니다 — 이 동작이 운영상 맞지 않으면 알려 주세요.
- 단독 방식: 설정 "개인정보 보관 기간"(30/90/180일, 기본 90일). 처리 끝난 접수가 기간을 넘었고 그 뒤 백업이 있으면 첫 화면에서 알린 뒤 사람이 눌러야 지웁니다. 이전 버전 사본(`versions[].snapshot`)도 비웁니다. 이렇게 지운 접수는 `.dgb` 백업에도 `pii_purged`(시각)와 빈 이름·연락처·주소로 들어갑니다 → PC `import_solo`는 빈 이름을 받을 수 있어야 합니다.

## 5. 목록 묶음: 지점의 행정동 `dong`

`dg.daylist/2` 압축 형식 지점 객체에 선택 키 추가:

```json
{ "q": 3, "i": "…", "r": "DG-20261103-0003", "v": 1, "n": "…", "p": "…", "a": "…", "d": "충장동", "it": [ … ] }
```

- 풀린 형식(`dg.daylist/1`)의 지점 필드 이름은 `dong`(문자열). 없으면 `""`.
- `pc/dgproto.py`: `compact_daylist`는 지점 dict의 `dong`이 비어 있지 않으면 `"d"`로 싣고, `expand_daylist`는 `"d"`가 없으면 `dong: ""`. `web/proto.js expandDaylist`도 같은 규칙. 형식 번호를 올리지 않았으므로 **v0.9 앱은 `"d"`를 무시하고 그대로 동작**, v0.10 앱은 `"d"` 없는 이전 묶음도 그대로 받습니다(상호 운용 시험 `tests/interop.mjs` 6번).
- PC가 할 일: `build_daylist`의 지점 dict에 `"dong": <행정동 이름>`을 넣기만 하면 됩니다(주소 위치 자료나 접수 입력에서). 휴대폰은 동을 카드에 표시하고, 2개 동 이상이면 동 거르기 단추, 노선 시간표는 동이 바뀌는 곳에 머리글을 보여 줍니다.
- 단독 방식 접수(`.dgb` 백업의 `state.requests[]`)에도 `dong` 필드(선택, 최대 20자)가 생겼습니다 → `import_solo`에서 받아 두면 됩니다.
- v0.10.1: 단독 방식 접수에서 주소 검색으로 주소를 고르면 `lat`·`lon`(WGS84, 소수 6자리)과 `geo_source: "ADDR"`이 함께 저장됩니다(지도로 지정하면 `MANUAL`, 내 위치면 `GPS`). PC `create_request`의 `geo_source` 규칙(`MANUAL`|`ADDR`)과 같습니다 — `GPS`는 PC에서 `MANUAL`로 받아도 됩니다.

### 5.1 반입지 좌표 (v0.10.1, 선택)

지점의 `"u"`(반입지 하차) 배열에 **5·6번째 값으로 반입지 위도·경도**를 넣을 수 있습니다. 휴대폰은 이 좌표로 [반입지 길안내]를 엽니다(표시 이름 `"반입지"`만).

```json
"u": ["11:40", "가상 반입지", 20, 5.5, 35.12345, 126.95678]
```

- 풀린 형식: `unload_after.lat`, `unload_after.lon` (없으면 `null`). 4개짜리 이전 형식도 그대로 받습니다(`tests/interop.mjs` 15번).
- **PC가 할 일(아직 안 됨)**: `pc/dgproto.py compact_daylist`에서 `u.get("lat")`, `u.get("lon")`이 있으면 `c["u"]`에 덧붙이고, `expand_daylist`도 같은 규칙. `routing.py`가 `unload_after`를 만들 때 `unload_site`의 `lat`/`lon`을 함께 넣기. PC `expand_daylist`는 5·6번째 값을 무시하므로 지금도 깨지지 않습니다.
- PC 목록에 반입지 좌표가 없으면 휴대폰에서 [하차 기록 → 반입지 위치 지정]으로 이 휴대폰에만 저장해 쓸 수 있습니다(PC로 보내지 않음).

## 6. 하루 중 목록 갱신 (휴대폰 동작, PC 변경 없음)

같은 날짜·더 높은 `assign_ver` 목록을 받으면 휴대폰이 이전 목록과 비교해 지점마다 `새로 추가` / `순서·시간 변경` / `정보 변경` 표시를 붙이고(그 지점을 열어 볼 때까지), "새 2곳, 변경 1곳, 빠짐 1곳" 요약을 보여 줍니다. 순서 변경은 상대 순서가 바뀐 곳만(가장 긴 증가 부분 수열 밖) 표시하므로 한 곳을 끼워 넣어도 나머지가 모두 "변경"이 되지는 않습니다.

## 7. 알려진 제한 (휴대폰)

- **Android 탭 새로고침(메모리 부족)**: 카메라 앱이 떠 있는 사이 브라우저가 앱 탭을 메모리에서 내리면, 돌아왔을 때 페이지가 새로 열리며 막 찍은 사진은 전달되지 않습니다(브라우저가 파일 선택 결과를 새 페이지에 넘기지 않음). 잠긴 상태로 돌아온 경우는 사진을 메모리에 잡아 두었다가 잠금 해제 뒤 저장하지만("사진 1장 저장 대기 — 잠금 해제 후 저장됩니다"), 탭이 다시 열린 경우는 다시 찍어야 합니다. 사진을 평문으로 임시 저장하지 않는다는 원칙 때문에 이 경우를 막는 저장소를 두지 않았습니다.
- 잠긴 사이 찍은 사진은 메모리에만 있으므로, 잠금 해제 전에 앱을 닫으면 사라집니다.
- 화면 켜짐 유지(Wake Lock)는 지원하는 브라우저에서만(iOS 16.4+ Safari, Android Chrome). 거절·미지원이면 아무 표시 없이 넘어갑니다.
- 지문·얼굴 잠금 해제는 WebAuthn **PRF 확장**을 지원하는 플랫폼 인증기에서만 켜집니다(Android Chrome 최신, iOS 18+ Safari 등). 지원하지 않으면 설정에 버튼이 나오지 않고 PIN만 씁니다. 데이터 키는 PRF 값에서 HKDF로 만든 키로 감싼 것만 저장합니다. 서버가 없어 인증 서명은 검증하지 않으며, 보호의 근거는 "PRF 값이 있어야 데이터 키가 풀린다"입니다.
- 배터리 알림은 Battery Status API가 있는 브라우저(Android Chrome)에서만. iOS는 표시 없음.
- 지도 미리 받기는 서비스 워커가 페이지를 제어할 때만(앱을 한 번 다시 연 뒤) 저장됩니다. 저장 한도 50MB, 오래 안 쓴 조각부터 지움. 줌 15 이상은 서비스 워커에서도 막습니다.
- 문자·길안내·전화는 휴대폰의 다른 앱을 여는 것이며, 보냈는지·도착했는지는 앱이 알 수 없습니다.
- 길안내 "앱 없음" 판단은 1.5초 안에 화면이 다른 앱으로 넘어가는지로 합니다. iOS Safari는 깔리지 않은 앱 주소를 열면 "주소가 유효하지 않음" 알림을 띄운 뒤 웹 지도로 넘어갑니다. 웹 지도는 새 창으로 열고, 팝업이 막히면 같은 창에서 엽니다(돌아오기는 뒤로 가기).
- 주소 검색은 실제 주소 서버에 연결해 시험하지 못했습니다(시험 환경에서 외부 연결이 막혀 있어 가짜 응답으로만 확인). 특히 **주소 서버가 브라우저 직접 호출(CORS)을 허용하는지 확인되지 않았습니다** → 8.1.

## 8. 외부 서비스 — 무엇을 어디로 보내는가 (v0.10.1)

v0.10.0까지는 "바탕 지도 서버 하나만, 주소 검색·길찾기 미사용"이었습니다. 사용자 요청으로 **주소 검색과 길안내를 더했고**, 원칙은 **"이름·연락처는 어떤 외부 서버나 지도 앱으로도 보내지 않는다"**로 바꿨습니다(README "보안·개인정보"의 외부 통신 줄은 PC 담당이 고쳐야 함).

| 서비스 | 받는 곳 | 보내는 것 | 보내지 않는 것 | 언제 |
| --- | --- | --- | --- | --- |
| 바탕 지도 | `tiles.openfreemap.org` (HTTPS, 기존) | 지도 조각 번호(줌 14 이하, 약 2km 격자), 양식·글꼴 | 이름·연락처·주소·핀 좌표 | 지도 화면, 미리 받기 |
| 주소 검색 | `https://business.juso.go.kr/addrlink/addrLinkApi.do` (GET) | `confmKey`(검색 승인키), `currentPage=1`, `countPerPage=10`, `keyword`(검색칸에 적은 낱말), `resultType=json` | 이름·연락처·메모·접수번호, 쿠키·Referer | 단독 접수·위치 지정 화면에서 2자 이상 적고 300ms 쉬었을 때(또는 Enter) |
| 좌표 | `https://business.juso.go.kr/addrlink/addrCoordApi.do` (GET) | `confmKey`(좌표 승인키), 고른 결과의 `admCd`·`rnMgtSn`·`udrtYn`·`buldMnnm`·`buldSlno`, `resultType=json` | 위와 같음 | 검색 결과를 고를 때(좌표 승인키가 있을 때만) |
| 길안내 | **통신 아님** — 휴대폰의 지도 앱을 엶 | 목적지 좌표(소수 6자리), 표시 이름 `N번 수거지`/`반입지`, (네이버) `appname`=앱 주소 | 이름·연락처·주소·접수번호 | [길안내]·[다음 길안내]·[반입지 길안내] |

- CSP(`web/index.html`): `connect-src 'self' https://tiles.openfreemap.org https://business.juso.go.kr` — 주소 서버 하나만 더했습니다. `script-src 'self'` 그대로(JSONP 안 씀).
- 검색어 안전장치: 검색어에 그 접수의 이름(2자 이상)·연락처(8자리 이상)가 들어 있으면 보내지 않고 "주소 낱말만 적어 주세요"라고 알립니다. 서버가 거부하는 특수문자(`% = < > [ ]` 등)는 빼고 40자로 자릅니다.
- 승인키: 설정 → 주소 검색에 "주소 검색 승인키"와 "좌표 승인키"(주소정보누리집에서 기관이 따로 발급)를 넣습니다. 다른 설정처럼 업무 상태(AES-GCM, PIN으로 감싼 키)에 암호화 저장되고, [정리] 뒤에도 유지됩니다. 승인키가 없으면 검색칸이 꺼지고 "승인키를 설정에서 입력" 안내 → 직접 입력·지도에서 위치 지정.
- 좌표 변환: 좌표 API의 `entX`/`entY`(UTM-K, EPSG:5179, GRS80, 원점 38°N·127.5°E, 축척 0.9996, 가산 1,000,000/2,000,000)를 휴대폰 `web/juso.js utmkToWgs84`로 WGS84로 바꿉니다. `pc/dgpc/geo.py`와 같은 식이며, 시험에서 두 구현이 1mm 이내로 일치합니다(`tests/interop.mjs` 13번). 출입구 좌표이므로 배출 위치와 다를 수 있어 화면에 그렇게 안내합니다.
- 동 제안: 검색 결과의 행정동(`hemdNm`)이 있으면 그 이름, 없으면 법정동(`emdNm`)을 동구 행정동 13곳 + 이 휴대폰에서 쓴 동 이름과 맞춥니다. `계림동`처럼 행정동이 둘(계림1·2동)이면 후보 단추로 고르게 합니다.

### 8.1 CORS와 "주소 검색 경로"

- 설정 "주소 검색 경로: **직접** / **PC 경유**". 기본은 단독 방식 = 직접, PC 연결 방식 = PC 경유.
- 직접: 휴대폰이 `fetch`(`mode: cors`, `credentials: omit`, `referrerPolicy: no-referrer`)로 바로 묻습니다. 주소 서버가 `Access-Control-Allow-Origin`을 주지 않으면 브라우저가 응답을 막아 "주소 검색 서버에 연결하지 못했습니다(인터넷 또는 브라우저 차단)"가 뜨고, 직접 입력·지도 지정으로 넘어갑니다. **행안부 예제는 JSONP(`callback`)를 쓰므로 CORS가 허용되지 않을 가능성이 있습니다** — 실제 승인키·기기로 꼭 확인해 주세요. JSONP는 외부 스크립트 실행이라 CSP(`script-src 'self'`) 원칙상 쓰지 않았습니다.
- PC 경유: 휴대폰과 PC는 실시간 연결이 없으므로(QR·파일로만 주고받음) **휴대폰에서는 검색하지 않고**, PC 연결 방식에서는 PC가 주소·좌표를 정해 목록으로 보냅니다(PC 쪽 주소 검색은 별도 구현). 직접 호출이 CORS로 막히는 것이 확인되면 단독 방식도 PC 작업으로 돌리거나, 기관 중계 서버를 두어야 합니다.

### 8.2 길안내 주소 형식 (`web/nav.js`)

| 앱 | 앱 주소 | 앱이 없을 때 |
| --- | --- | --- |
| 카카오맵 (기본) | `kakaomap://route?ep={위도},{경도}&by=CAR` (출발지 생략 = 현재 위치) | `https://map.kakao.com/link/to/{N번 수거지},{위도},{경도}` |
| T맵 | `tmap://route?goalx={경도}&goaly={위도}&goalname={N번 수거지}` | 웹 길안내 없음 → 기본 지도 앱 |
