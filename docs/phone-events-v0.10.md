# 휴대폰 앱 v0.10 — 새 기록 종류·목록 필드·외부 서비스 (PC 반영용 규격)

> v0.10.1 추가: 길안내 기본 켬(앱 4종), 주소 검색(행정안전부 도로명주소 API), 반입지 좌표 — 2.5, 3장 `LOCATION_FIX`, 5.1, **8장(외부 서비스)** 참고.
>
> v0.11(PC v0.11 + 휴대폰 0.11.0) 추가: PC 서버가 대신 묻는 행안부 주소 검색, 카카오모빌리티 도로 이동시간, 배정 화면 카카오맵 링크, 목록 묶음 지점의 감면율 `"rd"`·부과번호 `"lv"` — **8.3~8.5** 참고.

대상: PC 결과 가져오기(`pc/dgpc/service.py import_result`) 담당. 휴대폰 앱 v0.10.0(`web/`)이 결과 파일(`dg.result/1`)에 새로 넣는 기록과, 목록 묶음(`dg.daylist/2`)에 새로 받을 수 있는 필드를 정리합니다.

## 0. 결론 요약

- 결과 파일 형식(`dg.result/1`)·봉투·서명은 **바뀌지 않았습니다.** 기록(`events[]`)의 `kind`가 7개 늘고, 기존 기록 본문에 선택 필드가 몇 개 붙습니다.
- 현재 PC 코드(`import_result`)는 모르는 `kind`를 `result_event`에 `APPLIED`로 저장하고 `derive()`에서는 무시합니다(읽어서 확인함). 그래서 **지금 PC로도 가져오기는 실패하지 않습니다.** 아래 표의 "PC 권장 처리"는 화면에 보여 주려면 할 일입니다.
- 주의: `request_id`가 빈 기록 중 `UNLOAD`가 아닌 것은 지금 PC에서 "PC에 없는 접수" 충돌이 됩니다. 그래서 휴대폰은 **새 팀 단위 기록을 만들지 않습니다**(작업자 교대도 기록이 아니라 각 기록 본문의 `worker`로만 남김).
- (해결됨) 취소된 접수의 `ARRIVE`·`SMS_INTENT`·`NAV_INTENT`·`STICKER_CHECK`·`FEE_NOTICE`도 지금 PC는 충돌함으로 보내지 않습니다(`service.py` `CANCELLED_OK_KINDS`).
- 목록 묶음: 지점에 선택 키 `"d"`(행정동 이름) 추가. **형식 번호는 그대로 `dg.daylist/2`.** `pc/dgproto.py`의 `compact_daylist`/`expand_daylist`에 이미 반영했습니다(지점 dict에 `dong`이 있으면 실림, 없으면 생략).

## 1. 모든 기록 공통

결과 파일의 기록 한 건(기존과 같음):

```json
{ "event_id": "uuid", "seq": 57, "request_id": "uuid", "assign_ver": 2, "base_req_ver": 1,
  "kind": "ARRIVE", "body": { ... }, "device_ts": "2026-11-03T01:05:12.345Z" }
```

### 새 공통 본문 필드 `worker` (선택)

설정에서 작업자 이름을 정해 두면 **모든 기록**(기존 종류 포함, `UNLOAD` 포함)의 `body.worker`에 지금 작업자의 짧은 이름(최대 10자, 예: `"김수거"`)이 들어갑니다. 작업자를 정하지 않았으면 필드가 없습니다. 교대(작업자 바꾸기)는 PIN 없이 이름만 바뀌며 따로 기록하지 않습니다.

PC 권장 처리: 접수 상세의 현장 기록 목록에 작업자 열로 표시. 주민 정보가 아니므로 결과 파일에 들어가는 것이 원칙(이름·연락처·주소 미포함)과 충돌하지 않습니다. 변경 이력(audit)에는 넣지 않아도 됩니다.

## 2. 새 기록 종류 (`kind`)

| kind | 언제 | 진행 상태에 셈 | PC 권장 처리 |
| --- | --- | --- | --- |
| `ARRIVE` | 상세 화면 [도착] | 예 (방문 전 → 처리 중) | 도착 시각·위치 오차 표시. 위치는 접수 좌표를 바꾸지 않음 |
| `STICKER_CHECK` | 품목별 스티커·신고필증 확인 | 예 | 품목 행 옆에 확인/없음/번호 불일치 표시 |
| `FEE_NOTICE` | 현장 금액이 접수 때보다 늘었을 때 고지 | 예 | 수납 기록 화면에 "추가 금액 안내: 동의/안내함/거부" 표시 |
| `SMS_INTENT` | [문자]로 문자 앱 열기 | **아니오** | 연락 이력에 "문자 안내(종류)" 표시 |
| `NAV_INTENT` | [길안내]·[다음 길안내]로 지도 앱 열기 (v0.10.1부터 항상 켬) | **아니오** | 표시만(선택) |

"진행 상태에 셈"은 휴대폰 `fees.js deriveStop`의 `progress` 계산(`NON_PROGRESS` 목록)입니다. PC `derive()`의 `has_field_records`는 지금 `FIELD_ITEM_ADD`·`ITEM_RESULT`·`ATTEMPT`만 세므로 그대로 두어도 상태가 잘못 바뀌지 않습니다.

### 2.1 `ARRIVE`

```json
{ "lat": 35.146213, "lon": 126.923301, "acc": 12, "worker": "김수거" }
```

- 위치 권한이 없거나 설정 "도착·사진에 휴대폰 위치 남기기"를 끈 경우 본문은 `{}`(또는 `worker`만).
- `lat`/`lon`: 소수 6자리, `acc`: 미터(정수). 휴대폰 GPS 값이며 배출 위치가 아님 → `LOCATION_FIX`처럼 접수 좌표를 바꾸면 안 됩니다.
- 시각은 기록의 `device_ts`.
- 같은 지점에서 여러 번 누를 수 있음(마지막 것이 현재 값).

### 2.2 `STICKER_CHECK`

```json
{ "line_id": "uuid", "result": "MISMATCH", "number": "2611-0042", "decision": "LEAVE", "worker": "김수거" }
```

- `result`: `OK`(확인) | `MISSING`(없음) | `MISMATCH`(번호 불일치)
- `number`: 불일치일 때 붙어 있던 번호(선택, 최대 30자). 주민 정보 아님.
- `decision`: `MISSING`/`MISMATCH`일 때만. `COLLECT`(그래도 수거) | `LEAVE`(미수거)
- `LEAVE`이면 바로 뒤에 같은 `line_id`의 `ITEM_RESULT`(`qty_collected: 0`, `reason: "NO_STICKER"`)가 따로 옵니다. 수량 계산은 기존 `ITEM_RESULT` 규칙 그대로.
- `line_id`는 접수 품목 또는 현장 추가 품목(`FIELD_ITEM_ADD`)의 행 ID.

### 2.3 `FEE_NOTICE`

```json
{ "received": 17000, "total": 26000, "extra": 9000, "pending": 1, "response": "AGREED", "worker": "이수거" }
```

- `received`: 접수 당시 금액(확정 단가 행 합), `total`: 현장 확인 수량 기준 확인된 소계, `extra = total − received`(> 0일 때만 기록), `pending`: 금액 확인 대기 행 수(소계에서 빠짐).
- `response`: `AGREED`(동의) | `NOTIFIED`(주민에게 안내함, 답 없음) | `REFUSED`(거부 — 해당 품목 미수거)
- `REFUSED`이면 본문에 `"lines": ["line_id", ...]`가 붙고, 그 앞에 각 행의 `ITEM_RESULT`(`reason: "FEE_REFUSED"`)가 옵니다. 현장 추가 품목은 `qty_collected: 0`, 접수 품목은 접수 수량을 넘는 만큼만 미수거.
- 휴대폰은 결과(수거 완료·일부 수거)를 저장하기 전에, 같은 금액 이상으로 고지한 기록이 없으면 이 창을 띄웁니다. 금액 자체(수수료 계산 규칙)는 바뀌지 않습니다 — 기록일 뿐 수납 완료가 아닙니다.

### 2.4 `SMS_INTENT`

```json
{ "template": "SOON", "worker": "김수거" }
```

- `template`: `SOON`(곧 도착) | `ABSENT`(부재 안내) | `REVISIT`(재방문 안내). 문구 **내용과 번호는 기록하지 않습니다.**
- 문자는 휴대폰 문자 앱이 보내며 앱은 보냈는지 알 수 없습니다(문자 앱을 연 기록).

### 2.5 `NAV_INTENT`

```json
{ "app": "kakao", "worker": "김수거" }
```

- `app`(v0.10.1): `kakao`(카카오맵) | `tmap`(T맵) | `naver`(네이버지도) | `geo`(기본 지도 앱, Android `geo:`) | `apple-maps`(기본 지도 앱, iOS `maps://`). 설정 "길안내 앱"에서 고른 앱(기본 카카오맵). v0.10.0이 만든 기록은 `geo`·`apple-maps`만 있습니다.
- 지도 앱에는 목적지 좌표와 표시 이름 `"N번 수거지"`(N = 방문 순번)만 넘깁니다. 이름·연락처·주소·접수번호는 넘기지 않습니다(8.2).
- 앱이 없어 웹 지도·기본 지도 앱으로 넘어간 경우도 기록은 한 건(처음 고른 앱 이름)입니다. 실제로 안내를 받았는지는 알 수 없습니다.
- 결과 저장 뒤 아래 고정 영역의 **[다음 길안내]**는 다음 미완료 지점을 열며, 그 기록은 **다음 지점의 `request_id`**로 남습니다.
- **반입지 길안내는 기록하지 않습니다**(접수가 없는 팀 기록은 PC에서 "PC에 없는 접수" 충돌이 되므로 — 0장 주의 참고).

## 3. 기존 기록 본문에 붙는 선택 필드

| kind | 새 필드 | 뜻 |
| --- | --- | --- |
| `PHOTO_META` | `taken_at` (ISO) | 사진을 받은 시각(촬영 직후). 기존 필드 `photo_id, phase, sha256, bytes, line_id` 그대로 |
| `PHOTO_META` | `file_ts` (ISO 또는 null) | 카메라가 준 파일 시각 |
| `PHOTO_META` | `lat`, `lon`, `acc` (선택) | 위치 권한이 이미 허용된 경우만(촬영 때 권한 창을 띄우지 않음). 사진 바이트에는 EXIF 위치가 없음(다시 그려 저장) |
| `ATTEMPT` | `no_photo_reason` (선택) | 부재·배출 안 됨으로 `NOT_COLLECTED`를 저장할 때 사진이 없으면 필수: `DARK`(어두움) · `REFUSED`(주민 촬영 거부) · `CAMERA`(카메라 고장) · `OTHER` |
| `ITEM_RESULT` | `reason` 새 값 | `NO_STICKER`(스티커·필증 없음·불일치), `FEE_REFUSED`(추가 금액 거부). 기존 값 `NOT_PUT_OUT, DIFFERENT, CANNOT_LOAD, POSTPONED, OTHER` 그대로 |
| `LOCATION_FIX` | `source: "GPS"`, `acc` (선택) | 지도 조각을 못 받아 [지금 내 위치로 이동]으로 휴대폰 위치를 저장한 경우. 지도로 맞춘 경우는 기존처럼 `source: "MANUAL"` |
| `LOCATION_FIX` | `source: "ADDR"` (v0.10.1) | 위치 지정 화면에서 주소 검색 결과(건물 출입구 좌표)를 그대로 저장한 경우. PC `geo_source`의 `ADDR`과 같은 뜻. 검색 뒤 지도를 움직여 맞추면 `MANUAL` |
| (모두) | `worker` | 1장 참고 |
| (지운 기록) | `pii_purged: true` | 4장 참고 — 휴대폰 안에서만 생김. 보관 종료 확인 뒤에 지우므로 결과 파일로는 보통 나가지 않음 |

PC 권장 처리: 사유 코드 표(`NO_STICKER`, `FEE_REFUSED`)를 PC 화면 사유 이름표에 더하기. "부재 증거" 확인: `ATTEMPT.outcome = NOT_COLLECTED` 이면서 그 접수의 `PHOTO_META`가 없으면 `no_photo_reason`이 있어야 정상.

## 4. 휴대폰 쪽 개인정보 지우기 (PC가 할 일 없음, 참고)

- PC 연결 방식: [결과 보내기]에 **보관 종료 확인 코드**를 넣으면, 그 목록에서 결과가 끝난(`DONE`·`PARTIAL`·`NOT_COLLECTED`) 지점 중 기록이 모두 PC에 반영된 곳의 이름·연락처·주소·상세 위치·메모·좌표를 휴대폰에서 지웁니다(카드에 "개인정보 정리됨"). 수량·결과·사진 기록은 사진 회수까지 남깁니다. 그 지점의 기록에서 메모 글(`FIELD_MEMO.text`)·좌표(`lat/lon/acc`)도 지웁니다.
- 새 날짜 목록을 받으면(이전 결과가 모두 확인된 경우만 받을 수 있음 — 기존 규칙) 이전 목록은 새 목록으로 바뀌고, 이전 날짜 기록의 메모 글·좌표도 지웁니다.
- 같은 날 새 갱신본을 받아도 이미 지운 지점은 지운 채로 둡니다(PC가 다시 보내도 휴대폰에 다시 두지 않음). PC가 재방문을 위해 다시 보낸 경우 휴대폰에서는 접수번호로만 보입니다 — 이 동작이 운영상 맞지 않으면 알려 주세요.
- 단독 방식: 설정 "개인정보 보관 기간"(30/90/180일, 기본 90일). 처리 끝난 접수가 기간을 넘었고 그 뒤 백업이 있으면 첫 화면에서 알린 뒤 사람이 눌러야 지웁니다. 이전 버전 사본(`versions[].snapshot`)도 비웁니다. 이렇게 지운 접수는 `.dgb` 백업에도 `pii_purged`(시각)와 빈 이름·연락처·주소로 들어갑니다 → PC `import_solo`는 빈 이름을 받을 수 있어야 합니다.

## 5. 목록 묶음: 지점의 행정동 `dong`

`dg.daylist/2` 압축 형식 지점 객체에 선택 키 추가:

```json
{ "q": 3, "i": "…", "r": "DG-20261103-0003", "v": 1, "n": "…", "p": "…", "a": "…", "d": "충장동", "it": [ … ] }
```

- 풀린 형식(`dg.daylist/1`)의 지점 필드 이름은 `dong`(문자열). 없으면 `""`.
- `pc/dgproto.py`: `compact_daylist`는 지점 dict의 `dong`이 비어 있지 않으면 `"d"`로 싣고, `expand_daylist`는 `"d"`가 없으면 `dong: ""`. `web/proto.js expandDaylist`도 같은 규칙. 형식 번호를 올리지 않았으므로 **v0.9 앱은 `"d"`를 무시하고 그대로 동작**, v0.10 앱은 `"d"` 없는 이전 묶음도 그대로 받습니다(상호 운용 시험 `tests/interop.mjs` 6번).
- PC가 할 일: `build_daylist`의 지점 dict에 `"dong": <행정동 이름>`을 넣기만 하면 됩니다(주소 위치 자료나 접수 입력에서). 휴대폰은 동을 카드에 표시하고, 2개 동 이상이면 동 거르기 단추, 노선 시간표는 동이 바뀌는 곳에 머리글을 보여 줍니다.
- 단독 방식 접수(`.dgb` 백업의 `state.requests[]`)에도 `dong` 필드(선택, 최대 20자)가 생겼습니다 → `import_solo`에서 받아 두면 됩니다.
- v0.10.1: 단독 방식 접수에서 주소 검색으로 주소를 고르면 `lat`·`lon`(WGS84, 소수 6자리)과 `geo_source: "ADDR"`이 함께 저장됩니다(지도로 지정하면 `MANUAL`, 내 위치면 `GPS`). PC `create_request`의 `geo_source` 규칙(`MANUAL`|`ADDR`)과 같습니다 — `GPS`는 PC에서 `MANUAL`로 받아도 됩니다.

### 5.1 반입지 좌표 (v0.10.1, 선택)

지점의 `"u"`(반입지 하차) 배열에 **5·6번째 값으로 반입지 위도·경도**를 넣을 수 있습니다. 휴대폰은 이 좌표로 [반입지 길안내]를 엽니다(표시 이름 `"반입지"`만).

```json
"u": ["11:40", "가상 반입지", 20, 5.5, 35.12345, 126.95678]
```

- 풀린 형식: `unload_after.lat`, `unload_after.lon` (없으면 `null`). 4개짜리 이전 형식도 그대로 받습니다(`tests/interop.mjs` 15번).
- **PC가 할 일(아직 안 됨)**: `pc/dgproto.py compact_daylist`에서 `u.get("lat")`, `u.get("lon")`이 있으면 `c["u"]`에 덧붙이고, `expand_daylist`도 같은 규칙. `routing.py`가 `unload_after`를 만들 때 `unload_site`의 `lat`/`lon`을 함께 넣기. PC `expand_daylist`는 5·6번째 값을 무시하므로 지금도 깨지지 않습니다.
- PC 목록에 반입지 좌표가 없으면 휴대폰에서 [하차 기록 → 반입지 위치 지정]으로 이 휴대폰에만 저장해 쓸 수 있습니다(PC로 보내지 않음).

## 6. 하루 중 목록 갱신 (휴대폰 동작, PC 변경 없음)

같은 날짜·더 높은 `assign_ver` 목록을 받으면 휴대폰이 이전 목록과 비교해 지점마다 `새로 추가` / `순서·시간 변경` / `정보 변경` 표시를 붙이고(그 지점을 열어 볼 때까지), "새 2곳, 변경 1곳, 빠짐 1곳" 요약을 보여 줍니다. 순서 변경은 상대 순서가 바뀐 곳만(가장 긴 증가 부분 수열 밖) 표시하므로 한 곳을 끼워 넣어도 나머지가 모두 "변경"이 되지는 않습니다.

## 7. 알려진 제한 (휴대폰)

- **Android 탭 새로고침(메모리 부족)**: 카메라 앱이 떠 있는 사이 브라우저가 앱 탭을 메모리에서 내리면, 돌아왔을 때 페이지가 새로 열리며 막 찍은 사진은 전달되지 않습니다(브라우저가 파일 선택 결과를 새 페이지에 넘기지 않음). 잠긴 상태로 돌아온 경우는 사진을 메모리에 잡아 두었다가 잠금 해제 뒤 저장하지만("사진 1장 저장 대기 — 잠금 해제 후 저장됩니다"), 탭이 다시 열린 경우는 다시 찍어야 합니다. 사진을 평문으로 임시 저장하지 않는다는 원칙 때문에 이 경우를 막는 저장소를 두지 않았습니다.
- 잠긴 사이 찍은 사진은 메모리에만 있으므로, 잠금 해제 전에 앱을 닫으면 사라집니다.
- 화면 켜짐 유지(Wake Lock)는 지원하는 브라우저에서만(iOS 16.4+ Safari, Android Chrome). 거절·미지원이면 아무 표시 없이 넘어갑니다.
- 지문·얼굴 잠금 해제는 WebAuthn **PRF 확장**을 지원하는 플랫폼 인증기에서만 켜집니다(Android Chrome 최신, iOS 18+ Safari 등). 지원하지 않으면 설정에 버튼이 나오지 않고 PIN만 씁니다. Galaxy의 **Samsung Pass**는 등록 응답에는 PRF를 주지 않고 다음 인증부터 주므로, 앱은 등록 직후 한 번 더 인증해 PRF 값이 실제로 나오는지로 판단합니다(0.12.1, 그 전에는 "지원하지 않음"으로 잘못 막았음). 등록 때 지문을 두 번 묻는 것은 이 때문입니다. 0.12.4부터는 두 번째 인증을 **새로 누른 단추**([지문·얼굴 확인])에서 합니다(일부 브라우저는 단추를 누른 직후에만 인증 창을 허용). 또 Android Chrome이 키 보호를 지원하는 패스키 저장소(Google 비밀번호 관리자·Samsung Pass)를 쓰도록 검색 가능한 패스키(`residentKey: required`)로 만들고, 실패하면 설정에 단계·오류 이름을 남깁니다(개인정보 없음). 데이터 키는 PRF 값에서 HKDF로 만든 키로 감싼 것만 저장합니다. 서버가 없어 인증 서명은 검증하지 않으며, 보호의 근거는 "PRF 값이 있어야 데이터 키가 풀린다"입니다.
- 배터리 알림은 Battery Status API가 있는 브라우저(Android Chrome)에서만. iOS는 표시 없음.
- 지도 미리 받기는 서비스 워커가 페이지를 제어할 때만(앱을 한 번 다시 연 뒤) 저장됩니다. 저장 한도 50MB, 오래 안 쓴 조각부터 지움. 줌 15 이상은 서비스 워커에서도 막습니다.
- 문자·길안내·전화는 휴대폰의 다른 앱을 여는 것이며, 보냈는지·도착했는지는 앱이 알 수 없습니다.
- 길안내 "앱 없음" 판단은 1.5초 안에 화면이 다른 앱으로 넘어가는지로 합니다. iOS Safari는 깔리지 않은 앱 주소를 열면 "주소가 유효하지 않음" 알림을 띄운 뒤 웹 지도로 넘어갑니다. 웹 지도는 새 창으로 열고, 팝업이 막히면 같은 창에서 엽니다(돌아오기는 뒤로 가기).
- 주소 검색은 실제 주소 서버에 연결해 시험하지 못했습니다(시험 환경에서 외부 연결이 막혀 있어 가짜 응답으로만 확인). 특히 **주소 서버가 브라우저 직접 호출(CORS)을 허용하는지 확인되지 않았습니다** → 8.1.

## 8. 외부 서비스 — 무엇을 어디로 보내는가 (v0.10.1)

v0.10.0까지는 "바탕 지도 서버 하나만, 주소 검색·길찾기 미사용"이었습니다. 사용자 요청으로 **주소 검색과 길안내를 더했고**, 원칙은 **"이름·연락처는 어떤 외부 서버나 지도 앱으로도 보내지 않는다"**로 바꿨습니다(README "보안·개인정보"의 외부 통신 줄은 PC 담당이 고쳐야 함).

| 서비스 | 받는 곳 | 보내는 것 | 보내지 않는 것 | 언제 |
| --- | --- | --- | --- | --- |
| 바탕 지도 | `tiles.openfreemap.org` (HTTPS, 기존) | 지도 조각 번호(줌 14 이하, 약 2km 격자), 양식·글꼴 | 이름·연락처·주소·핀 좌표 | 지도 화면, 미리 받기 |
| 주소 검색 | `https://business.juso.go.kr/addrlink/addrLinkApi.do` (GET) | `confmKey`(검색 승인키), `currentPage=1`, `countPerPage=10`, `keyword`(검색칸에 적은 낱말), `resultType=json` | 이름·연락처·메모·접수번호, 쿠키·Referer | 단독 접수·위치 지정 화면에서 2자 이상 적고 300ms 쉬었을 때(또는 Enter) |
| 좌표 | `https://business.juso.go.kr/addrlink/addrCoordApi.do` (GET) | `confmKey`(좌표 승인키), 고른 결과의 `admCd`·`rnMgtSn`·`udrtYn`·`buldMnnm`·`buldSlno`, `resultType=json` | 위와 같음 | 검색 결과를 고를 때(좌표 승인키가 있을 때만) |
| 길안내 | **통신 아님** — 휴대폰의 지도 앱을 엶 | 목적지 좌표(소수 6자리), 표시 이름 `N번 수거지`/`반입지`, (네이버) `appname`=앱 주소 | 이름·연락처·주소·접수번호 | [길안내]·[다음 길안내]·[반입지 길안내] |

- CSP(`web/index.html`): `connect-src 'self' https://tiles.openfreemap.org https://business.juso.go.kr` — 주소 서버 하나만 더했습니다. `script-src 'self'` 그대로(JSONP 안 씀).
- 검색어 안전장치: 검색어에 그 접수의 이름(2자 이상)·연락처(8자리 이상)가 들어 있으면 보내지 않고 "주소 낱말만 적어 주세요"라고 알립니다. 서버가 거부하는 특수문자(`% = < > [ ]` 등)는 빼고 40자로 자릅니다.
- 승인키: 설정 → 주소 검색에 "주소 검색 승인키"와 "좌표 승인키"(주소정보누리집에서 기관이 따로 발급)를 넣습니다. 다른 설정처럼 업무 상태(AES-GCM, PIN으로 감싼 키)에 암호화 저장되고, [정리] 뒤에도 유지됩니다. 승인키가 없으면 검색칸이 꺼지고 "승인키를 설정에서 입력" 안내 → 직접 입력·지도에서 위치 지정.
- 좌표 변환: 좌표 API의 `entX`/`entY`(UTM-K, EPSG:5179, GRS80, 원점 38°N·127.5°E, 축척 0.9996, 가산 1,000,000/2,000,000)를 휴대폰 `web/juso.js utmkToWgs84`로 WGS84로 바꿉니다. `pc/dgpc/geo.py`와 같은 식이며, 시험에서 두 구현이 1mm 이내로 일치합니다(`tests/interop.mjs` 13번). 출입구 좌표이므로 배출 위치와 다를 수 있어 화면에 그렇게 안내합니다.
- 동 제안: 검색 결과의 행정동(`hemdNm`)이 있으면 그 이름, 없으면 법정동(`emdNm`)을 동구 행정동 13곳 + 이 휴대폰에서 쓴 동 이름과 맞춥니다. `계림동`처럼 행정동이 둘(계림1·2동)이면 후보 단추로 고르게 합니다.

### 8.1 CORS와 "주소 검색 경로"

- 설정 "주소 검색 경로: **직접** / **PC 경유**". 기본은 단독 방식 = 직접, PC 연결 방식 = PC 경유.
- 직접: 휴대폰이 `fetch`(`mode: cors`, `credentials: omit`, `referrerPolicy: no-referrer`)로 바로 묻습니다. 주소 서버가 `Access-Control-Allow-Origin`을 주지 않으면 브라우저가 응답을 막아 "주소 검색 서버에 연결하지 못했습니다(인터넷 또는 브라우저 차단)"가 뜨고, 직접 입력·지도 지정으로 넘어갑니다. **행안부 예제는 JSONP(`callback`)를 쓰므로 CORS가 허용되지 않을 가능성이 있습니다** — 실제 승인키·기기로 꼭 확인해 주세요. JSONP는 외부 스크립트 실행이라 CSP(`script-src 'self'`) 원칙상 쓰지 않았습니다.
- PC 경유: 휴대폰과 PC는 실시간 연결이 없으므로(QR·파일로만 주고받음) **휴대폰에서는 검색하지 않고**, PC 연결 방식에서는 PC 접수 화면의 [주소 찾기]로 주소·좌표·동을 정해 목록에 실어 보냅니다. v0.11부터 PC [주소 찾기]는 이 PC의 주소 위치 자료에 더해 **PC 서버가 대신 묻는 행안부 검색**을 함께 보여 줍니다(8.3). 휴대폰 → PC로 검색을 넘기는 경로는 없습니다(앞으로도 실시간 연결을 두지 않는 한 없음). 직접 호출이 CORS로 막히는 것이 확인되면 단독 방식도 PC 작업으로 돌리거나, 기관 중계 서버를 두어야 합니다.

### 8.3 PC 서버의 행안부 주소 검색 대행 (v0.11, `pc/dgpc/external.py`)

PC 업무 화면(브라우저)은 여전히 바탕 지도 조각 서버에만 직접 연결합니다(CSP `connect-src`도 그대로). 주소 검색은 **PC 서버(`pc_tool.py serve`)가 대신** 묻습니다.

| 서비스 | 받는 곳 | 보내는 것 | 보내지 않는 것 | 언제 |
| --- | --- | --- | --- | --- |
| 주소 검색 | `https://business.juso.go.kr/addrlink/addrLinkApi.do` (GET, 서버 → 행안부) | `confmKey`, `currentPage=1`, `countPerPage=10`, `keyword`(주소 찾기 칸 검색어, 특수문자 제거·40자), `resultType=json` | 이름·연락처·메모·접수번호·부과번호, 쿠키·Referer | 접수 화면 [주소 찾기]에 2자 이상 적고 300ms 쉬었을 때(승인키가 있을 때만) |
| 좌표 | `…/addrlink/addrCoordApi.do` (GET) | 좌표 승인키, 고른 결과의 `admCd`·`rnMgtSn`·`udrtYn`·`buldMnnm`·`buldSlno`(숫자 형식만 통과), `resultType=json` | 위와 같음 | 행안부 결과를 고를 때(좌표 승인키가 있을 때만) |

- 화면 API: `GET /api/juso-search?q=<검색어>&name=<이름 칸 값>` → `{configured, items[], total, coord, blocked?, error?}`, `GET /api/juso-coord?admCd=…&rnMgtSn=…&udrtYn=…&buldMnnm=…&buldSlno=…` → `{lat, lon}` 또는 `{none, reason}`, `POST /api/external/test {"service":"juso"|"kakao"}`(관리자, 고정 검색어 `동구청`·차고지 부근 좌표로 연결 시험). 접수 담당자·관리자만(팀장·수거팀 계정은 403).
- 검색어 안전장치(서버에서): 전화번호 모양(`0\d{1,2}-?\d{3,4}-?\d{4}`) 또는 숫자 8자리 이상, 접수 화면 이름 칸 값(2자 이상)이 들어 있음, 이 PC에 저장된 주민 이름(3자 이상은 포함, 2자는 같음)과 겹침 → 보내지 않고 "주소 낱말만 적어 주세요" 안내.
- 결과 합치기: 이 PC 주소 위치 자료 결과가 먼저, 그 아래 `행안부` 표시 결과(같은 도로명+건물번호는 뺌). 고르면 주소(`도로명주소 (법정동, 건물명)`), 좌표(`entX`/`entY` UTM-K → `geo.utmk_to_wgs84`, 출처 `ADDR`), 동(`hemdNm`이 행정동 목록에 있으면 그것, 아니면 `emdNm`, 그래도 없으면 `area.detect_dong`)을 채웁니다.
- 승인키: 설정 → **주소·외부 서비스** 탭에 "주소 검색 승인키"·"좌표 승인키". SQLCipher 암호화 DB(`meta`)에만 저장, 저장 뒤 화면에는 `••••` + 끝 4자리만 돌아옵니다. 변경 이력에는 키 이름만(값 없음).
- 기록: 접속기록에 `SEARCH` 한 줄("행안부 주소 검색 (검색어 기록 안 함)", 건수만). 서버 로그(`state/logs/server.log`)는 원래대로 경로 틀만 남기고 조건(query)은 버리므로 검색어가 남지 않습니다. 오류 문구에도 요청 주소·검색어를 넣지 않습니다.
- 네트워크: 시간 제한 5초. 기관망 프록시는 서버 실행 환경의 `HTTPS_PROXY`/`NO_PROXY`(urllib 기본)를 따르고, 자체 서명 프록시 인증서는 `SSL_CERT_FILE`로 지정합니다. 받는 곳은 `DG_JUSO_BASE`로 바꿀 수 있습니다(자동 시험의 가짜 서버용, 기본 `https://business.juso.go.kr`).

### 8.4 도로 이동시간: 카카오모빌리티 (v0.11, `pc/dgpc/routing.py`)

설정 → 주소·외부 서비스 → **이동시간 계산 방식**: `직선거리 추정`(기본, 외부 전송 없음) / `로컬 OSRM`(기본 설정의 `http://127.0.0.1` OSRM) / `카카오모빌리티 API`(REST 키). 예전 DB처럼 방식을 고른 적이 없으면 OSRM 주소가 있을 때 OSRM, 없으면 직선거리 추정입니다.

| 받는 곳 | 보내는 것 | 보내지 않는 것 |
| --- | --- | --- |
| `https://apis-navi.kakaomobility.com/v1/destinations/directions` (POST, 출발지 1 → 목적지 최대 30곳, `radius` 10000m, `priority=TIME`) | `Authorization: KakaoAK <REST 키>`, 출발지·목적지 좌표(경도 `x`·위도 `y`, 소수 5자리), 목적지 순번 `key`(0,1,2…) | 이름·연락처·주소·접수번호·동 |
| `…/v1/directions?origin=경도,위도&destination=경도,위도&priority=TIME` (GET) | 위와 같음 — 반경 10km 밖 쌍만 | 위와 같음 |

- 행렬: 지점(차고지·수거지·반입지·종료지) 좌표를 소수 5자리로 묶어 같은 좌표는 한 번만 묻고, 출발지마다 30곳씩 나눠 한 행씩 채웁니다. 결과(초)는 분으로 올림.
- 캐시: 암호화 DB `travel_cache(origin, dest, seconds, fetched_at)` — 좌표 쌍 → 초, 30일 지나면 쓰지 않고 지웁니다. 이름·주소는 없습니다.
- 한도·실패: 호출 사이 0.05초 간격, 한 번 계산에 최대 300회·30초, 각 호출 5초 제한. 인증 실패(401/403)·연결 실패·시간 초과·429·5xx가 나면 그 자리에서 더 묻지 않습니다. 못 구한 쌍(실패·경로 없음·한도 초과)은 **그 쌍만 직선거리 추정**으로 채우고 배정 화면에 `도로 시간: 카카오모빌리티 (일부 직선 추정 3쌍)`처럼 표시합니다. 하나도 못 구하면 `직선거리 추정(도로 아님) — 카카오모빌리티로 구하지 못함: <이유>`.
- 기록: 노선 계산마다 변경 이력에 `ROUTE_MATRIX`(호출 수·캐시 사용 수·추정 쌍 수만). 받는 곳은 `DG_KAKAO_NAVI_BASE`로 바꿀 수 있습니다(시험용).
- 주의: 노선 계산 중(최대 30초) PC 서버의 다른 요청이 기다립니다(DB 잠금). 출발 시각별 교통 반영(`departure_time`)은 쓰지 않습니다.

배정·노선 화면의 지점마다 **카카오맵** 링크(새 창)가 있습니다: `https://map.kakao.com/link/to/{N번 수거지},{위도},{경도}` — 휴대폰 `web/nav.js`와 같은 형식이며 좌표와 `N번 수거지`만 담습니다. 누르기 전에는 아무 요청도 가지 않습니다.

### 8.5 목록 묶음: 감면율 `"rd"`·부과번호 `"lv"` (v0.11, 선택 키)

`dg.daylist/2` 지점 객체에 선택 키 두 개를 더했습니다. **형식 번호는 그대로**이며 없으면 이전과 같습니다.

```json
{ "q": 2, "i": "…", "r": "DG-20261103-0002", "lv": "2026-01-00002", "rd": 50, "it": [ … ] }
```

| 키 | 풀린 형식 필드 | 뜻 | 없을 때 |
| --- | --- | --- | --- |
| `"rd"` | `reduction: {rate}` | 감면율(%, 정수 1~100). PC `request.reduction_rate`(감면 사유가 있고 0보다 클 때만) | `reduction: null`(Python은 키 없음) — 감면 없음 |
| `"lv"` | `levy_no` | 부과번호(PC `request.levy_no`, `연도-동코드-일련번호`) | `""` |
| `"ru"` (v0.13) | `reduction: {rate, round_unit}` | 감면액 끝수 단위(원). PC `request.reduction_round_unit`(감면을 적용·바꿀 때의 설정값)이 **10원일 때만** 싣습니다. `"rd"`가 없으면 무시 | 1원(`round_unit` 키 없음) — 원 미만 버림 |

- 감면 **사유 이름(예: 기초생활수급자)은 휴대폰에 보내지 않습니다** — 복지 대상 여부는 현장에 필요 없는 민감 정보라서 감면율만 싣습니다. 휴대폰은 `감면 (50%)`로 표시합니다.
- 휴대폰 금액(`web/fees.js calcFee`): 계산 금액 = 현장 확인 수량 기준 금액(현장 추가 품목 포함) → 감면액 = `floor(계산 금액 × 감면율 / 100)`를 끝수 단위(`"ru"`, 없으면 1원) 미만 버림 → 부과 금액 = 계산 금액 − 감면액. PC `finance.fee_summary`와 같은 규칙입니다(`tests/interop.mjs` 17·17b번, 공통 벡터 `data/derive_vectors.json`에서 두 구현 대조). 금액 확인 대기가 있으면 셋 다 미확정.
- 화면: 지점 상세에 `부과번호 …`, 계산 내역 아래 `계산 금액 → 감면 (율%) → 부과 금액`(주민이 낼 금액). 현장 금액 고지 창에도 감면 적용 뒤 늘어나는 부과 금액을 함께 보여 줍니다. 결과 파일(`FEE_NOTICE` 등)의 금액 필드는 그대로 **감면 전 계산 금액**입니다.
- 하루 중 목록 갱신: 감면율·끝수 단위가 바뀌면 그 지점에 `정보 변경` 표시(감면 없는 지점·1원 단위 지점의 비교 값은 이전과 같음).
- `"ru"`는 v0.13에서 더했습니다. 0.12 이하 휴대폰은 모르는 키를 무시하므로 10원 단위 감면 건을 1원 단위로 보여 줄 수 있습니다(PC가 원본 — PC 금액이 맞음). 휴대폰도 함께 올리세요.
- 상호 운용: PC `compact_daylist` → 휴대폰 `expandDaylist`, 휴대폰 쪽 v2 자료 → PC `expand_daylist`, 이전 형식(키 없음) 양쪽 모두 `tests/interop.mjs` 17번, PC 단위 시험 `tests/test_pc.py v11_external`.

## 9. PC 연결 방식의 요청 기록 (v0.12, PC v0.12 + 휴대폰 0.12.0)

단독 방식에만 있던 접수·수정·취소를 PC 연결 방식에서도 하되, PC가 원본이므로 휴대폰은 **요청 기록**을 결과 파일에 넣고 PC가 확인합니다. PC v0.11 이하는 이 종류를 모르므로(알 수 없는 접수 → 충돌함) PC를 먼저 올려야 합니다.

| `kind` | 본문 | PC 처리 |
| --- | --- | --- |
| `FIELD_INTAKE` | `temp_no`, `channel`(현장·전화·방문, 0.12.7 — 없으면 현장), `name`, `phone`, `address`, `dong`, `spot_note`, `memo`, `planned_date`, `eta`, `items[]`(`line_id`, `fee_rate_id`, `name`, `spec`, `unit`, `unit_label`, `qty`), 선택 `lat`·`lon` | `request_id`(휴대폰이 만든 UUID)로 접수를 만듦. 경로 '현장', `origin_device`=보낸 기기, 사무실 확인 전(`field_checked_at` 없음). 금액은 PC 표로 다시 계산(휴대폰 단가 무시), PC 표에 없는 품목은 확인 대기. 품목 행 ID를 그대로 써서 뒤따르는 `ITEM_RESULT` 등이 이어짐. 형식 오류면 만들지 않고 충돌함. 기록에는 개인정보 없이 `temp_no`·품목 수·예정일만 남김 |
| `CORRECTION` | `fields`{`name`/`phone`/`address`/`spot_note`/`planned_date` 중 바뀐 것}, `reason` | 늘 충돌함(사유 "현장 정정 요청 — 사무실 확인 필요"). [반영] = 원본 수정 + 이전 내용 버전 보존, 주소가 바뀌면 동 다시 판별·좌표 지움, 예정일이 바뀌면 활성 배정 해제. 처리 뒤 본문은 바꾼 칸 이름만 |
| `CANCEL_REQUEST` | `code`(`RESIDENT`·`DUPLICATE`·`ITEM_REFUSED`·`OUT_OF_AREA`·`OTHER`), `text` | 늘 충돌함(사유 "현장 취소 요청 — 사무실 확인 필요"). [반영] = 그 사유 코드로 취소(이력에 "현장 요청 · 사무실 확인: 사유"), 납부가 있으면 환불 필요 |

- 현장 접수 지점의 기록은 `assign_ver`=0. PC는 **그 접수를 만든 기기**가 보낸 갱신본 0 기록을 배정 기록 없이 받습니다(다른 기기·다른 팀은 지금처럼 충돌함).
- 가져오기 결과 요약에 `field_intakes`(만든 현장 접수 수), `review`(확인 대상 요청 수)가 붙습니다. `review`는 `conflict`에 더하지 않습니다.
- 휴대폰: 새 목록에 같은 `request_id`가 오면 PC 것을 쓰고 현장 접수 사본을 내립니다. 반영 확인(보관 종료 확인 코드) 뒤 `FIELD_INTAKE`의 이름·연락처·주소와 `CORRECTION`의 값은 지우고 칸 이름만 남깁니다.
- 방문 순서 바꾸기는 휴대폰 안에서만(`localOrder`) — PC로 보내는 기록이 없습니다.


## 10. 휴대폰 0.13.0 — 결과 반영 정보·코드 이름·복원·저장 (PC 반영용)

### 10.1 목록 묶음의 결과 반영 정보 `"rel"` (선택 키, `dg.daylist/2` 그대로)

| 키 | 값 | 뜻 |
| --- | --- | --- |
| `"rel"` (목록 맨 위) | `{"seq": 정수 ≥ 0, "ph": ["사진 UUID", …], "g": [["세대", 정수 ≥ 0], …]}` | `seq`: PC가 **이 기기의 세대 없는(이전 앱) 기록 1..seq를 빠짐없이** 가져온 번호. `ph`: PC가 해시를 대조해 회수한 이 기기 사진 ID. `g`(선택, 10.7): 세대별로 **그 세대 첫 번호부터 빠짐없이** 가져온 번호 |

- 넣는 곳: PC는 `build_daylist` 결과 dict에 `"rel"`을 넣기만 하면 됩니다. `pc/dgproto.py compact_daylist`가 `norm_rel`로 검사해 실습니다(정수가 아니거나 음수, `ph`가 UUID 목록이 아니면 **키를 빼고** 이전 형식으로). `expand_daylist`·휴대폰 `expandDaylist`(`web/proto.js normRel`)도 같은 검사로 읽고, 틀리면 없는 것으로 봅니다. 사진 ID는 소문자·중복 제거.
- 봉투 안(서명·암호화된 평문)에 있으므로 휴대폰은 PC 값으로 믿습니다(`tests/interop.mjs` 20번: 봉투를 바꾸면 `AUTH_FAIL`).
- 휴대폰 처리(`web/field.js applyRelease`): rel이 받았다고 말하는 자기 기록 = **결과 반영 코드를 넣은 것과 같음**(`releasedSeq` 올림, 그 범위의 결과 파일 반영 확인, 끝난 곳 개인정보 정리). 어느 기록이 '받음'인지는 10.7(세대). 받지 않은 기록은 미전송 그대로. 작은 값은 되돌리지 않음(단조 증가). `ph` 중 이 휴대폰이 아는 사진 = **사진 회수 코드를 넣은 것과 같음**. PC가 아는 번호(`seq`, 다른 세대의 `g`)가 휴대폰 번호보다 크면(오래된 백업 복원 등) 휴대폰 번호도 그 뒤로 올려 PC에 있는 번호를 다시 쓰지 않습니다(지금 세대에 기록이 있으면 새 세대를 시작해 세대 안 번호는 빈틈없이).
- 목록을 받지 않는 경우(지난 날짜·오래된 갱신본 등)에도 `rel`은 먼저 적용합니다.
- PC `release_info`(`pc/dgpc/assign.py`): `seq`·`g` 모두 "빠짐없이 받은 마지막 번호"입니다(중간 번호가 빠지면 그 앞에서 멈춤). 휴대폰은 rel이 말한 번호까지 반영됨으로 처리하고, 나중 [오늘 자료 정리]에서 그 기록을 지웁니다.
- 코드 입력은 계속 됩니다(목록을 못 받는 날·이전 PC).

### 10.2 코드 세 가지 이름 (화면 표시만 바뀜, 코드 형식 그대로)

| 이름 | 방향 | 앞 글자 | 이전 이름 |
| --- | --- | --- | --- |
| 수신 코드 | 휴대폰 → PC (목록을 받았다는 확인) | `R-` | 수신 확인 코드 |
| 결과 반영 코드 | PC → 휴대폰 (결과 파일 가져옴) | `D-` | 보관 종료 확인 코드 |
| 사진 회수 코드 | PC → 휴대폰 (사진 파일 회수) | `P-` | 사진 회수 확인 코드 |

- 휴대폰은 앞 글자를 코드 옆에 따로 그립니다. 수신 코드의 `.fp`(PC에 불러 주는 값)는 지금처럼 8자만입니다.
- 입력칸은 앞 글자를 붙여 넣어도(`d-abcd 2345`) 떼고 받습니다. 결과 칸에 사진 회수 코드(또는 `P-`)를, 사진 칸에 결과 반영 코드를, 어느 칸에든 자기 수신 코드를 넣으면 맞는 칸을 알려 주고 받지 않습니다(`F.checkCode`).
- **PC 제안(바꾸지 않았음)**: ① PC 화면·`pc_tool.py` 출력에 `D-XXXX XXXX`, `P-XXXX XXXX`로 표시하고 이름을 위 표대로. ② 수신 코드 입력은 앞에 `R-`가 붙어 와도 떼고 비교(공백·하이픈 무시). ③ 8자 코드 자체(HMAC → 31자 알파벳)는 그대로 — 앞 글자는 코드에 넣지 않으므로 이전 휴대폰과도 맞습니다. 앞 글자를 코드 계산에 넣고 싶으면(다른 종류 코드를 수학적으로 구별) `receipt_code(ack, bundle_id)`의 HMAC 입력 `b"ack"`를 종류별(`b"ack-R"`·`b"ack-D"`·`b"ack-P"`)로 바꾸는 방법이 있으나, 양쪽 동시 배포가 필요해 이번에는 하지 않았습니다.

### 10.3 백업 복원 (PC 연결 방식)

- 복원은 이제 **합칩니다**(`web/field.js mergeRestore`): 기록 번호 `seq` = max(지금, 백업), `releasedSeq` = max, 기록은 `event_id`로 합침(지금 휴대폰에만 있던 기록도 남김), 결과 파일·사진 파일·회수 확인 합침, 목록은 더 새 것. 서로 다른 기록이 같은 번호면 백업 쪽을 두고 나머지를 맨 뒤 번호로 옮깁니다(PC가 이미 받았으면 `event_id`로 중복 처리).
- 결과: 복원 뒤 새 기록이 PC에 있는 번호를 다시 쓰지 않습니다 → PC `seq_reused` 경고·충돌 없음(`tests/interop.mjs` 22번, `tests/e2e.py pc_sync`). 단독 방식은 백업으로 바꾸되 `seq`만 지킵니다.
- 복원하면 늘 **새 기록 세대**를 시작합니다(10.7). 번호를 옮긴 기록도 새 세대로 적습니다. 휴대폰 자료를 잃고 오래된 백업으로 복원하면 지금 번호를 모르므로 백업 번호 다음부터 쓰게 되는데(PC가 이미 본 번호), 세대가 다르므로 PC가 그 번호를 '받음'으로 알려도 새 기록은 반영되지 않습니다.

### 10.4 같은 날 갱신본 (휴대폰 동작, PC 변경 없음)

PC가 중간 결과를 가져온 뒤 같은 날 목록을 다시 만들면, 이 휴대폰이 기록한 지점이 `revisit`·`prior_collected`·빠진 줄·방문 약속으로 돌아옵니다. 휴대폰은 **그 지점에 자기 기록이 있으면** 이전 목록 값(재방문 아님, 빠진 줄 되살림, 수량, 자기가 남긴 재방문 약속)으로 되돌려 기록이 '오래된 것'처럼 보이거나 '재방문·정보 변경'으로 표시되지 않게 합니다(`F.carryOver`). 단가·금액 상태 변경(사무실 확정 단가)은 새 목록 것을 씁니다. 자기 기록이 없는 지점은 PC 값 그대로입니다.

### 10.5 저장소

- `navigator.storage.persist()` 결과를 `st.storagePersisted`에 남기고, 거절이면 첫 화면에 알림([다시 요청]·[알겠습니다]).
- 사진 저장 전 `storage.estimate()`: 남은 공간이 사진×2+2MB보다 적으면 저장하지 않고 대기열에 둠, 50MB 아래면 알림. `QuotaExceededError`·잠김은 사진을 버리지 않고 대기열에 남김(첫 화면 [사진 다시 저장]). 상태 저장 실패는 기존처럼 화면 위 띠(메모리 기록 유지).
- **기록을 키별(추가만)로 나누는 것은 하지 않았습니다.** 지금은 `s:state` 하나에 전체 상태를 암호화해 매번 다시 씁니다(하루 기록 수천 건 ≈ 수백 KB, 한 번 쓰기 수 ms~수십 ms). 나누면 `e:<seq>` 키 + 상태에서 `events` 빼기 + 처음 열 때 옮기기 + 백업·정리·지우기·복원·PII 지우기(이벤트 본문을 고치는 `purgeEventPII`)를 모두 바꿔야 하고, 옮기는 중 실패 시 기록 유실 위험이 있어 현장 시험 전에는 하지 않습니다. 하게 되면: 1) 새 키에 모두 쓰고 확인 2) 상태에서 `events` 삭제 순서, `state.eventsSplit=1` 표시.

### 10.6 업데이트(서비스 워커)

- [업데이트]는 잠겨 있거나 수량·기록·사진 저장이 남아 있으면 미룹니다. 다른 창의 업데이트로 서비스 워커가 바뀌어도(controllerchange) 저장 대기 사진·저장 실패 기록이 있으면 새로 열지 않고, 끝난 뒤 엽니다.
- `sw.js activate`는 지금 버전과 **바로 앞 버전** 캐시를 남기고 그보다 오래된 것만 지웁니다. 지금 캐시에 없는 파일은 앞 버전 캐시에서 찾습니다(아직 새로 열지 않은 창). 제한: 창별 버전을 추적하지 않으므로 두 번 연속 업데이트하는 동안 열린 채인 아주 오래된 창은 앞앞 버전 파일을 못 찾을 수 있습니다(새로 열면 해결).

### 10.7 기록 세대 `gen` (휴대폰 0.13.0, PC 구조 4단계)

검토 지적: 휴대폰 자료를 잃고 **오래된 백업**으로 복원하면(지금 번호를 모름) 새 기록이 PC가 이미 받은 번호(예: PC는 1~20, 백업은 10까지 → 새 기록 11번)를 다시 씁니다. PC는 새 `event_id`면 받고 경고만 남기지만, 그 전에 휴대폰이 `rel.seq = 20`인 목록을 받으면 아직 보내지 않은 11번을 '받음'으로 처리하고 개인정보까지 지웠습니다. 기록에 **세대**를 붙여 막습니다.

| 어디 | 키 | 값 |
| --- | --- | --- |
| 휴대폰 상태 | `gen` | 지금 세대(8자리 소문자 16진수, 무작위). 처음 쓸 때(이전 버전 자료 포함) 만들고, **백업에서 복원할 때마다** 새로 만듦 |
| 휴대폰 상태 | `gens` | `[{gen, start}]` 세대별 첫 번호(최근 16개). 새 세대 첫 번호 = 그때 `seq + 1` |
| 휴대폰 상태 | `genRestored` | 복원한 적 있음 → 세대 없는(이전 버전) 기록은 `rel.seq`로 반영하지 않음(코드 입력으로만) |
| 기록(결과 파일 `events[]`) | `gen` (선택) | 그 기록의 세대. 이전 앱 기록에는 없음 |
| 결과 파일 맨 위 | `gens` (선택) | `[["세대", 첫 번호], …]` 이 파일에 든 기록의 세대와 그 세대 첫 번호. 첫 기록이 빠져도 PC가 첫 번호를 앎 |
| 목록 `rel` | `g` (선택) | `[["세대", n], …]` 최근 4개 세대(첫 번호가 큰 것부터). 그 세대 첫 번호부터 n까지 PC가 빠짐없이 받음. 첫 번호를 못 받은 세대는 싣지 않음 |

- 휴대폰 규칙(`web/field.js relCovers`): 세대 있는 기록은 `rel.g`에 그 세대가 있고 `휴대폰이 아는 첫 번호 ≤ seq ≤ n`일 때만 받음. 세대 없는 기록은 `genRestored`가 아니고 `seq ≤ rel.seq`일 때만. `releasedSeq`는 번호 순으로 '받음'이 아닌 첫 기록 앞에서 멈춥니다(그 뒤 받은 기록은 다시 보내면 PC가 `event_id`로 건너뜀).
- 검사(`pc/dgproto.py norm_rel`·`norm_gens`, `web/proto.js normRel`·`normGens` 같은 규칙): 세대는 `^[0-9a-f]{8}$`, 번호는 0 이상 정수(참거짓 아님), 짝 2개, 16개 이하. 틀리면 **`g`만 뺌**(rel은 그대로 = 이전 동작). 같은 세대가 두 번이면 큰 번호.
- PC(구조 4단계 `_m4_device_gen`): `result_event.gen`(세대, 이전 기록 NULL), `device_gen(device_id, gen, start_seq, first_seen_at, last_seen_at)`(첫 번호 = 머리 `gens`와 받은 번호 중 작은 것), `result_seq(device_id, gen, seq)`(받은 번호: 반영·충돌·거부, **이미 받은 `event_id`도** — 복원 때 번호를 옮긴 기록). 이전 기록은 4단계에서 세대 `''`로 채움. `rel.seq`는 세대 `''`만, 1부터.
- 최근 가져오기의 '휴대폰 확인(DAYLIST)'(`ops._rel_covered`)도 세대별로 봅니다: 가져온 뒤에 만든 목록이고 그 rel이 가져온 기록의 세대별 가장 큰 번호를 덮어야 함.
- 이전 PC(세대를 모름): 휴대폰은 `g`가 없으므로 세대 있는 기록을 목록으로 반영하지 않습니다(코드 입력으로). 이전 휴대폰(세대 없음): PC는 지금처럼 `rel.seq`로 알립니다.
- 시험: `tests/interop.mjs` 22-1(실제 PC로 검토 시나리오: A 1~20 → 10까지 든 백업 복원 → B의 11번은 rel(A:20)로 반영 안 됨 → 가져온 뒤 rel에 B:11 → 반영), 22-2(규칙·양방향 형식), `tests/test_pc.py` 8-1, `tests/e2e.py pc_sync`(복원 뒤 기록이 새 세대로 PC에 저장).
