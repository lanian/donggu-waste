# 배포·운영 안내 (운영·정보화 담당자용)

이 문서는 **휴대폰 앱 배포 절차, 자동 시험(CI), PC 프로그램 업데이트·백그라운드 실행, 로그, 점검 목록**과 **기관이 결정해야 할 사항**을 정리합니다. 업무 화면 사용법은 [운영매뉴얼](운영매뉴얼.md)을 보세요.

## 1. 한눈에 보기

| 무엇 | 어디서 | 언제 바뀌나 |
| --- | --- | --- |
| 휴대폰 앱(`web/`) | GitHub Pages (현재 `https://lanian.github.io/donggu-waste/`) | **v 태그**(예: `v0.10.0`)를 달거나 수동 실행하고, 승인자가 승인했을 때만 |
| PC 프로그램(`pc/`) | 각 업무 PC | 운영 담당자가 아래 4장 절차로 직접 업데이트할 때만 (자동 업데이트 없음) |
| 업무 자료 | PC의 암호화 DB(`pc/state/`), 휴대폰 안 | 저장소·Pages·CI에는 **절대 없음** (시험은 가상 자료만) |

## 2. 자동 시험(CI) 개요

`.github/workflows/ci.yml` 하나로 시험과 배포를 합니다.

| 작업 | 내용 | 배포를 막나 |
| --- | --- | --- |
| 앱 버전 검사 | `tools/check_version.py` — `web/app.js`의 `APP_VERSION` = `web/sw.js`의 `VERSION`, 태그로 실행하면 태그(`v` 뺀 값)도 같아야 함. `sw.js`가 미리 저장하는 파일이 모두 있는지도 확인 | 예 |
| 단위·로직 시험 (Linux) | 포함 라이브러리 대조, 수수료표 생성물 대조, `npm test`, `python tests/test_pc.py` | 예 |
| 화면 종단 시험 ×2 | Playwright Chromium으로 `tests/e2e.py`(휴대폰 화면), `tests/e2e_pc.py`(PC 화면). 실패하면 화면 캡처를 **Artifacts**(`shots-e2e…`, 14일 보관)로 올림 | 예 |
| PC 로직 시험 (Windows·macOS, 참고용) | 고정 의존성을 바이너리 휠로만 설치 → SQLCipher 동작 확인 → `tests/test_pc.py`. 결과는 실행 요약(Summary)에 표시 | **아니오** (경고만) |
| 휴대폰 앱 배포 | 위 세 작업이 모두 통과하고, **v 태그 push** 또는 **main·v 태그에서 수동 실행**일 때만. `github-pages` 환경 승인 대기 후 `web/`만 올림 | — |

언제 무엇이 실행되나:

- **main에 push, PR**: 시험만. 배포하지 않습니다. (문서 `*.md`, `docs/`만 바뀐 push·PR은 건너뜀)
- **`v*` 태그 push**: 시험 → 승인 → 배포
- **Actions 탭 → "CI · Pages 배포" → Run workflow**: 고른 브랜치·태그로 시험 → (main 또는 v 태그면) 승인 → 배포

화면 종단 시험은 시험 중 바탕 지도 서버(`tiles.openfreemap.org`)에 접속합니다. GitHub 실행기는 인터넷이 되므로 문제없고, 시험 자체가 "외부 요청은 지도 서버뿐, 개인정보 없음"을 검사합니다.

로컬에서 같은 시험: `npm run test:all` (또는 `npm run check:version`, `npm test`, `npm run test:pc`, `npm run test:e2e`). 화면 시험은 `CHROME` 환경변수로 브라우저 경로를 바꿀 수 있습니다(기본 `/usr/bin/google-chrome`).

## 3. 휴대폰 앱 배포(릴리스) 절차

### 3.1 저장소 관리자 1회 설정 (필수)

GitHub 저장소 **Settings**에서:

1. **Pages → Build and deployment → Source: GitHub Actions**
2. **Environments → `github-pages`**
   - **Required reviewers**: 승인자 1명 이상 지정(예: 운영 책임자, 정보화 담당). **Prevent self-review** 켜기 — 태그를 단 사람이 스스로 승인하지 못하게
   - **Deployment branches and tags → Selected branches and tags**: `main` 브랜치와 **태그 규칙 `v*`** 추가. (기본값은 main만 허용이어서, 이것을 빼면 태그 배포가 "환경 보호 규칙" 오류로 거부됩니다)
3. **Rules → Rulesets** (권장)
   - `main` 브랜치: PR 필수, 필수 상태 검사 `앱 버전 검사`, `단위·로직 시험 (Linux)`, `화면 종단 시험 (e2e)`, `화면 종단 시험 (e2e_pc)`, 강제 push 금지
   - 태그 `v*`: 만들기·지우기·옮기기를 관리자만 (배포 기준이 되는 태그 보호)
4. **Actions → General → Workflow permissions: Read repository contents** (배포 작업만 Pages 권한을 따로 받음)
5. 배포 계정(저장소 관리자·승인자) 2단계 인증 필수, 퇴직·전보 시 즉시 제외

### 3.2 새 버전 내보내기

1. 바뀐 내용을 main에 병합하고 main의 시험이 모두 녹색인지 확인
2. 버전 올리기 — **두 곳을 같은 값으로**: `web/app.js`의 `APP_VERSION`, `web/sw.js`의 `VERSION` (예: `0.10.0`). `sw.js` 버전이 바뀌어야 휴대폰에 "새 버전이 있습니다 [업데이트]"가 뜹니다. 운영매뉴얼 제목의 버전도 맞춥니다
3. 로컬 확인: `python tools/check_version.py --tag v0.10.0`
4. 커밋을 main에 병합한 뒤 그 커밋에 태그:
   ```bash
   git checkout main && git pull
   git tag -a v0.10.0 -m "v0.10.0: 바뀐 점 요약"
   git push origin v0.10.0
   ```
5. Actions에서 실행이 시험을 통과하면 **"Review deployments"** 대기 상태가 됩니다. 승인자가 바뀐 점과 시험 결과를 보고 **Approve and deploy**
6. 배포 후 확인: 업무용 휴대폰 1대에서 앱을 닫았다 열어 [업데이트] → 설정 화면의 버전 확인 → PC와 목록 받기·결과 보내기 1회 시험
7. 수거팀에 "미전송 결과를 보낸 뒤 [업데이트]"를 안내 (업무 중 강제 업데이트 없음)

태그와 앱 버전이 다르면 "앱 버전 검사"가 실패하고 배포되지 않습니다. 태그를 잘못 달았으면 태그를 지우고(`git push --delete origin v0.10.0`) 버전을 고친 커밋에 다시 답니다.

### 3.3 되돌리기

- **권장: 고친 새 버전으로 앞으로 배포**(예: 문제 커밋 되돌림 + `0.10.1`). 휴대폰은 버전이 바뀌어야 새 앱을 받습니다.
- 급할 때: Actions → Run workflow → **Use workflow from: 이전 태그(예: v0.9.1)** 로 수동 실행 → 승인. 이전 앱 파일이 다시 올라가지만, 이미 새 버전을 받은 휴대폰은 앱 [업데이트]가 떠야 바뀌므로 수거팀 안내가 필요합니다.
- 휴대폰 앱과 PC 사이 전송 형식이 바뀐 버전이면 PC도 같은 시점에 맞춰야 합니다(릴리스 설명에 표시).

## 4. PC 프로그램 업데이트

### 4.1 원칙

- **먼저 백업**, 그다음 업데이트. 업무 시간 외(마감 후)에 합니다.
- 코드는 **태그(배포된 버전)** 기준으로 받습니다. main의 중간 상태를 업무 PC에 넣지 않습니다.
- 의존성은 고정본(`pc/requirements.txt`, 버전·해시 고정)으로만 설치합니다. 다른 파일이 내려오면 설치가 멈춥니다.
- **DB 구조 변경(마이그레이션)은 프로그램 시작 때 자동**으로 적용됩니다. 한 번 새 구조로 바뀐 DB는 옛 버전 코드에서 열리지 않을 수 있으므로, 되돌릴 때는 **업데이트 전 백업**으로 복원합니다.
- 가상환경(`.venv`) 사용을 권장합니다. 아래 서비스 설정 파일도 `.venv`를 가정합니다.
  ```
  python -m venv .venv
  .venv\Scripts\pip install -r pc\requirements.txt        (Windows)
  .venv/bin/pip install -r pc/requirements.txt           (Linux·macOS)
  ```

### 4.2 순서

1. **백업**: 설정 → [지금 백업] → [열어 확인] (또는 `python pc/pc_tool.py backup`). 백업 파일을 보안 매체에 복사
2. **멈춤**: 서비스로 돌리면 서비스를 멈춤(6장), 아니면 서버 창에서 Ctrl+C
3. **자료 폴더 복사**: 멈춘 상태에서 `pc/state/` 폴더 전체(또는 `DG_STATE`로 지정한 폴더)를 날짜 붙여 복사 — 가장 빠른 되돌림 수단
4. **코드 바꾸기** — 둘 중 하나
   - **git 사용(권장)**: `git fetch --tags` → `git checkout v0.10.0` (로컬에서 고친 파일이 있으면 멈추고 확인)
   - **zip 사용(망분리 PC 등)**: 인터넷 PC에서 GitHub 릴리스/태그의 *Source code (zip)* 을 받아 승인된 매체로 반입 → 새 폴더에 풀기 → 옛 폴더의 `pc/state/`를 새 폴더의 `pc/state/`로 **옮기기**(새 zip에는 state가 없음). 자료 폴더를 코드 밖에 두려면 `DG_STATE` 환경변수로 지정(예: `D:\DongguData\state`) — 그러면 코드 폴더만 통째로 바꾸면 됩니다
   - 망분리 PC는 의존성도 미리 받아 반입: 인터넷 PC(같은 OS·Python 버전)에서 `pip download -r pc/requirements.txt -d wheels` → 반입 → `pip install --no-index --find-links wheels -r pc/requirements.txt`
5. **의존성 설치**: `pip install -r pc/requirements.txt` (가상환경 안에서)
6. **시작**: 서비스 시작 또는 `python pc/pc_tool.py serve`. 시작 때 DB 마이그레이션 자동 적용 → 로그(7장)에 오류 없는지 확인
7. **확인**: 로그인 → 오늘 현황 → 접수 1건 조회 → 코드 버전 확인(`git describe --tags`, zip이면 폴더 이름의 태그). 휴대폰 앱도 같은 시기에 바뀌었다면 목록 전송·결과 가져오기 1회
8. **되돌리기**(문제가 있으면): 멈춤 → 이전 태그 코드로 되돌림 → 3번에서 복사한 `state/` 폴더로 바꾸거나 `python pc/pc_tool.py restore <백업.dgbak>` → 시작

### 4.3 의존성 고정·갱신 (개발·정보화 담당)

- 사람이 고치는 파일: `pc/requirements.in` (직접 의존성과 최소 버전)
- 설치에 쓰는 파일: `pc/requirements.txt` (모든 하위 패키지까지 버전·SHA-256 해시 고정, Windows·macOS·Linux 공용, Python 3.12 이상)
- CI 화면 시험용: `.github/requirements-e2e.txt` (위와 같은 버전 + Playwright)
- 다시 만들기:
  ```bash
  pip install uv
  uv pip compile pc/requirements.in --universal --python-version 3.12 --generate-hashes \
      --no-header --annotation-style line -o pc/requirements.txt          # 머리말 주석은 다시 붙이기
  uv pip compile .github/requirements-e2e.in -c pc/requirements.txt --universal --python-version 3.12 \
      --generate-hashes --no-header --annotation-style line -o .github/requirements-e2e.txt
  ```
  한 패키지만 올릴 때는 `--upgrade-package 이름`. 바꾼 뒤 PR을 열어 Windows·macOS 참고 시험까지 녹색인지 봅니다.
- 주기: 월 1회 보안 공지 확인(예: `pip install pip-audit && pip-audit -r pc/requirements.txt`), 보안 문제는 즉시 갱신
- GitHub Actions 버전은 Dependabot이 매주 갱신 PR을 엽니다(`.github/dependabot.yml`).

### 4.4 SQLCipher 설치가 안 될 때

- DB 암호화 모듈은 `sqlcipher3`(0.6.4)입니다. Windows(x64·x86·ARM64), macOS(Intel·Apple), Linux(x86_64·aarch64)용 **SQLCipher 내장 휠**이 Python 3.9~3.14용으로 배포되어 있어 보통은 컴파일 없이 설치됩니다. (예전 Linux 전용 `sqlcipher3-binary`는 더 쓰지 않습니다)
- "No matching distribution" 또는 C 컴파일러 오류가 나면: ① Python 버전이 3.12(64비트)인지 확인 ② `pip install --only-binary :all: -r pc/requirements.txt`로 소스 빌드를 막고 어떤 패키지에 휠이 없는지 확인 ③ 그 OS·Python용 휠이 정말 없으면 지원되는 Python 버전으로 바꿉니다. 소스 빌드(SQLCipher·OpenSSL 직접 빌드)는 업무 PC에서 하지 말고 정보화부서와 협의합니다.
- `sqlcipher3`가 없으면 프로그램이 평문 DB로 실행되지 않고 멈춥니다(의도된 동작).
- 설치 확인: `python -c "import sqlcipher3; print(sqlcipher3.connect(':memory:').execute('PRAGMA cipher_version').fetchone())"` → 버전 문자열이 나와야 함

## 5. DB 키와 무인 실행

서비스(백그라운드)로 실행하면 DB 키를 물어볼 수 없습니다. 반드시:

1. 서비스로 돌릴 **같은 사용자 계정**으로 터미널에서 `python pc/pc_tool.py init`을 한 번 실행해 DB 키를 운영체제 키 저장소(Windows 자격 증명 관리자 / macOS 키체인 / Linux Secret Service)에 넣습니다.
2. 그 계정으로 로그인한 상태에서 서비스가 키를 읽습니다. 그래서 Windows는 "로그온할 때 실행" 작업으로, Linux·macOS는 사용자 단위 서비스로 둡니다.
3. `DG_DB_KEY` 환경변수로 키를 주는 방식은 자동 시험용입니다. 운영에서 쓰려면(키 저장소가 없는 PC 등) 파일 권한을 본인만 읽기로 하고 정보보호 담당 승인을 받습니다.

## 6. 백그라운드 실행(서비스) 설정

템플릿: `tools/pc_service/`. 모두 **로그인한 담당자 계정**으로, 관리자 권한 없이, 꺼지면 10초 뒤 다시 시작합니다. 서버는 그대로 `127.0.0.1:8765`에서만 열립니다.

### Windows — 작업 스케줄러 (권장)

```powershell
# 저장소 폴더에서, 서비스로 돌릴 계정으로 (관리자 아님)
python -m venv .venv ; .venv\Scripts\pip install -r pc\requirements.txt
.venv\Scripts\python pc\pc_tool.py init            # 처음 한 번 (DB 키 → 자격 증명 관리자)
powershell -ExecutionPolicy Bypass -File tools\pc_service\windows\install_task.ps1
# 지우기: ... install_task.ps1 -Uninstall
```

- `donggu-pc-task.xml`: 로그온 30초 뒤 시작, 시간 제한 없음, 실패 시 1분 간격 10회 재시작, 중복 실행 안 함
- `run_server.ps1`: 서버를 실행하고 끝나면 10초 뒤 다시 시작(창 숨김). `.venv`가 없으면 PATH의 `python` 사용
- 멈춤·시작: 작업 스케줄러에서 `DongguWastePC` → 끝내기/실행, 또는 `Stop-ScheduledTask DongguWastePC` / `Start-ScheduledTask DongguWastePC`
- 업데이트할 때는 작업을 **끝내기**(실행 중인 python.exe도 끝났는지 작업 관리자에서 확인)

**NSSM(Windows 서비스)을 쓰려면**: 정보화부서가 NSSM 사용을 승인한 경우에만. Windows 서비스는 별도 계정으로 돌기 때문에 그 계정의 자격 증명 관리자에 DB 키가 있어야 합니다(또는 승인 하에 `DG_DB_KEY`).
```
nssm install DongguWastePC "C:\donggu-waste\.venv\Scripts\python.exe" "pc\pc_tool.py serve"
nssm set DongguWastePC AppDirectory C:\donggu-waste
nssm set DongguWastePC ObjectName .\업무계정 비밀번호
nssm set DongguWastePC AppEnvironmentExtra PYTHONUTF8=1
nssm set DongguWastePC AppStdout C:\donggu-waste\pc\state\logs\service.log
nssm set DongguWastePC AppStderr C:\donggu-waste\pc\state\logs\service.log
nssm set DongguWastePC AppRotateFiles 1
nssm set DongguWastePC AppRotateBytes 10485760
nssm set DongguWastePC AppExit Default Restart
nssm set DongguWastePC AppRestartDelay 10000
nssm start DongguWastePC
```

### Linux — systemd 사용자 단위

`tools/pc_service/linux/donggu-pc.service` 맨 위 주석대로 `~/.config/systemd/user/`에 복사 → `systemctl --user enable --now donggu-pc`. `Restart=always`, 10초 뒤 재시작, 콘솔 출력은 `pc/state/logs/service.log`, 상태는 `systemctl --user status donggu-pc`, `journalctl --user -u donggu-pc`.

### macOS — LaunchAgent

`tools/pc_service/macos/kr.donggu.waste.pc.plist`의 `/Users/USERNAME/donggu-waste`를 실제 경로로 바꾸고 주석대로 `launchctl bootstrap`. `KeepAlive`로 꺼지면 다시 시작.

## 7. 로그 위치

| 로그 | 위치 | 내용 |
| --- | --- | --- |
| 서버 로그 | `<자료 폴더>/logs/` — 기본 `pc/state/logs/` (`DG_STATE`를 지정했으면 그 아래 `logs/`) | 시작·마이그레이션·오류 등 서버 자체 기록 |
| 서비스 실행 기록 | 같은 폴더 `service.log` | 시작·종료 시각과 종료 코드(Windows), 콘솔 출력(Linux·macOS) |
| 실행별 콘솔 출력 (Windows) | 같은 폴더 `service-<시각>.out.log`, `.err.log` | 최근 40회분만 보관 |
| 변경 이력(감사) | 암호화 DB 안 → PC 화면 **사용자·이력** | 작업자·시각·대상·작업 |
| 배포 기록 | GitHub Actions 실행 기록·Environments → github-pages 배포 이력 | 누가 무엇을 언제 승인·배포했는지 |

- 로그 폴더는 자료 폴더 안에 있으므로 같은 접근 통제를 받습니다. 원칙적으로 로그에는 이름·연락처·주소를 남기지 않습니다(PC 화면 접근 로그 미기록). 점검 때 로그에 개인정보가 보이면 즉시 개발 담당에 알립니다.
- 로그를 메일·메신저로 보내야 하면 먼저 내용을 확인하고 필요한 부분만 보냅니다.

## 9. 기관 결정 필요

| 항목 | 결정할 내용 | 결정 전 현재 상태 |
| --- | --- | --- |
| **앱 배포 도메인** | 휴대폰 앱을 기관 도메인(예: `waste.dong-gu.go.kr`)으로 이전할지, 호스팅 위치(기관 웹서버/클라우드), 인증서·배포 계정 관리 주체 | 개인 GitHub Pages(`lanian.github.io`). 이전 시 주소가 바뀌므로 휴대폰에서 **새 주소로 다시 설치·기기 등록**이 필요하고, 옛 주소의 휴대폰 자료는 새 주소로 자동으로 옮겨지지 않음(전환 전 결과 모두 회수) |
| **여러 PC 사용(LAN 모드)** | 접수 PC가 2대 이상일 때 한 DB를 같은 망에서 함께 쓸지. 서버를 127.0.0.1 밖으로 여는 것이므로 **정보화부서 협의**(방화벽·망 구간, TLS 인증서, 접속 PC 제한, 서버 PC 지정·백업 책임) | 한 PC에서만(127.0.0.1). DB를 공유 폴더에 두는 방식은 금지 |
| **망분리 하 결과 파일 경로** | 휴대폰 결과 파일(.dgr)·사진 파일(.dgp)이 업무망 PC로 들어오는 승인 경로(업무 메일 → 망연계, 보안 USB 등)와 반입 검사 절차 | 업무 메일·보안 매체를 가정. 메일이 막히면 PC 웹캠 QR(역방향)로 결과만 회수 가능 |
| **길안내 앱 연동 허용** | 휴대폰에서 다음 지점으로 외부 길안내 앱(카카오맵·네이버지도·T맵 등)을 열도록 할지. 열면 그 앱 회사로 **주소·좌표가 전송**됨 | 미연동. 외부로 나가는 요청은 바탕 지도 조각뿐(주소·좌표 미전송) |
| **세외수입 연계 방식** | 수수료 부과·납부를 세외수입 시스템과 어떻게 맞출지(고지서 발행 주체, 납부 확인 자료를 파일로 받을지·수기로 입력할지, 대사 주기) | 담당자가 확인한 납부·환불을 PC에 기록만 함. 온라인 결제·자동 연계 없음 |
| **문자 발송 시스템 연계** | 접수 확인·방문 예정 안내 문자를 기관 문자 발송 시스템으로 보낼지, 발송 주체·문구·수신 동의, 연계 방식(파일 내보내기/연계 API) | 문자 발송 없음(수거팀이 휴대폰으로 직접 전화) |

이 밖에 [운영매뉴얼 9장 "운영 전 확인"](운영매뉴얼.md)의 항목(수수료표 시행일, 업무용 휴대폰·MDM, 보관 기간, 키 보관 책임자 등)도 함께 결정합니다.
