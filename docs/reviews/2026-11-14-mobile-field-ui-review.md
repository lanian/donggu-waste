## 검토 팀과 범위

- 현장 수거자 역할: 방문 → 연락 → 수량 → 사진 → 결과 → 다음 지점의 동선과 실수 가능성.
- 현장 접수·PC 전달 역할: 접수 입력, 품목·수량, 저장과 재진입, PC 입력 도움.
- 야외·접근성 역할: 큰 글씨, 테마, 고대비, 짧은 화면, 고정 버튼과 경고의 가림.

세 AI 검토자가 소스와 격리된 Chromium의 실제 PIN·암호화 IndexedDB를 사용했습니다. 자료는 가상이며 저장 실패·응답 지연·짧은 화면은 시험 조건입니다. 통합 검토자는 주요 수거·접수 시나리오를 별도 브라우저에서 재현하고 JSON·화면·호출 경로를 대조했습니다. 실제 현장 작업자 인터뷰나 물리 휴대폰 시험은 포함하지 않습니다.

## 우선 수정할 결함 4건

### P1-1. 접수 저장 실패를 성공으로 안내함

PC 연결 모드 전화 접수에서 실제 IndexedDB 쓰기를 실패시키면 `saveFailed=true`, `pending=true`이고 디스크의 기존 암호문도 바뀌지 않습니다. 그런데 “접수를 저장했습니다” 알림을 띄우고 입력 폼을 비운 뒤 홈으로 이동합니다. 홈의 기록 보호 안내와 성공 알림이 서로 모순됩니다. RAM과 대기 기록은 남아 있으므로 영구 유실이 확인된 것은 아닙니다.

- 근거: `web/screens/intake.js:176–181`, `web/core.js:245–256`. 편집·단독 저장 경로에도 반환값을 검사하지 않는 호출이 있어 함께 점검해야 합니다.
- 개선: 실제 저장 성공 후에만 성공 안내·폼 비우기·화면 이동을 수행합니다. 실패 시 입력과 최초 접수/이벤트 ID를 유지하고 저장 대기·재시도를 제공합니다.
- 증거: `recorder/results.json`, `recorder/failed-save-success.png`, `root-verify/results.json`.

### P1-2. 저장 응답 대기 중 반복 탭으로 접수가 중복 생성됨

첫 저장의 완료 응답을 보류하면 저장 버튼이 계속 활성화됩니다. 첫 탭에 1건, 둘째 탭에는 방금 만든 자기 접수의 중복 경고, 셋째 탭에는 같은 입력의 접수 2건이 됩니다. 첫 응답 전부터 서로 다른 request/event ID를 가진 `FIELD_INTAKE` 두 개가 생기며, 응답을 해제해도 두 건이 유지됩니다.

- 근거: `web/screens/intake.js:119–148`, `web/screens/intake.js:167–179`.
- 개선: 폼별 저장 진행 상태를 먼저 설정해 중복 실행을 막고 버튼을 잠급니다. 저장 여부 확인과 재시도는 새 접수를 만들지 않고 최초 작업을 재사용합니다. 별개 접수를 의도적으로 만드는 확인 흐름은 저장 완료 후에만 사용합니다.
- 증거: `recorder/results.json`의 탭별 0→1→1→2건·서로 다른 ID·같은 입력, `root-verify/results.json`.

### P1-3. 완료 후 수량을 고쳐도 완료 표시와 다음 이동이 유지됨

3개 전부 완료 저장 후 실은 수량을 2개로 줄이면 계산된 진행 상태는 `PARTIAL`인데 마지막 결과는 `DONE`입니다. 화면은 “저장됨: 수거 완료”를 유지하고 활성화된 “다음 2번 ▶”로 실제 이동할 수 있습니다. 재확정 안내문은 있지만 강제하지 않습니다. 이는 직전 문서에 남겨 둔 기존 제한이며 새 UI 회귀는 아닙니다.

- 근거: `web/screens/stop.js:367–410`, `web/screens/stop.js:436–458`.
- 개선: 마지막 결과 저장 뒤 수량·결과에 영향을 주는 값이 바뀌면 “결과 재확인 필요”를 표시합니다. 재선택·저장 전에는 완료 표시와 다음 이동을 보류하며, 기존 이력·이벤트 계약은 유지합니다.
- 증거: `collector/qty-edit-result.json`, `collector/after-complete-qty-edit.png`, `root-verify/qty-edit-result.json`.

### P1-4. 접수 수량 150에서 한 번 줄이면 99가 됨

단독 새 접수 → 품목 담기 → 실제 담기·증가 동작으로 150개 → 완료 → 접수 화면에서 − 버튼 순서로 150→99를 재현했습니다. 기대값은 149입니다. 수량을 직접 주입하지 않은 UI 경로에서도 발생합니다. 접수 화면이 공통 stepper의 기본 최대값 99를 사용합니다.

- 근거: `web/screens/intake.js:108`, `web/core.js:462–477`. 수거 상세의 명시적 9999 범위와 불일치합니다.
- 개선: 접수·품목 담기·수거 화면의 수량 범위를 일치시키고 한 번의 증감이 기존 값을 잘라내지 않게 합니다. 수량 변경에 따른 금액도 함께 검증합니다.
- 증거: `recorder/quantity-ui-result.json`, `recorder/quantity-ui.log`, `recorder/quantity-150-minus.png`.

## 개선 순서와 재검증 기준

1. 접수 저장 성공/실패 판정과 진행 중 중복 실행을 먼저 보완합니다. 지연·실패·재시도에서도 최초 ID와 입력이 유지되고 한 건만 저장되어야 합니다.
2. 수거 결과 재확정 상태와 수량 범위를 보완합니다. 150→149, 완료 후 수량 수정, 이전 수거분 보호와 다음 이동 조건을 검증합니다.
3. 수량 직접 입력·전체 채우기 확인·짧은 높이 배치를 다듬습니다. 정상/큰 글씨, 테마, 고대비, 경고 상태와 실제 휴대폰 키보드에서 큰 버튼을 누를 수 있어야 합니다.
