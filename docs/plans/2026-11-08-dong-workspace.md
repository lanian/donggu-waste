# PC 동별 통합 업무 설계·구현 계획

**Goal:** 전체 동 관리와 지정한 한 개·여러 동의 담당자 사용을 함께 지원하고, 동별 현황에서 접수와 배정까지 처리한다.

**승인된 방향:** 사용자는 동별 현황·접수·배정 통합 관리와 실제 동별 사용을 요청했고, 전체 동 선택 방식과 담당자 계정·자료 권한 분리를 모두 지원하도록 답했다. 기존 화이트·딥네이비 업무형 디자인과 단순한 화면 흐름을 유지한다.

**Architecture:** 기존 전체 업무 계정과 기존 API의 의미를 유지한다. 별도 `DONG` 역할과 담당 동 연결을 추가하고 동별 업무 전용 API에서 현재 계정·담당 동·대상 접수를 검사한다. 기존 전역 API의 역할 집합을 일괄 확대하지 않는다. 지정 동 계정은 허용된 전용 업무만 사용할 수 있어야 한다.

## 사용자·자료 범위

- 기존 ADMIN/INTAKE/LEAD의 전체 자료 권한은 유지한다. 기존 FIELD의 팀 범위도 유지한다.
- ADMIN/INTAKE/LEAD는 동별 관리에서 전체 또는 특정 동을 선택한다. LEAD는 기존처럼 조회만 한다.
- 새 DONG 계정은 ADMIN이 한 개 이상의 동을 지정한다. 지정 동 전체 또는 그중 한 동을 선택한다. FIELD는 새 업무 화면에 접근하지 않는다.
- 동은 안정된 `dong.id`로 연결한다. 이름 변경 후에도 담당 범위가 유지된다. 활성 DONG 계정에 담당 동이 없으면 자료를 볼 수 없고 전체로 대체하지 않는다.
- DONG에 기존 전역 API 권한을 부여하지 않는다. bootstrap·내 계정·암호·화면 설정처럼 필요한 자기 정보 경로만 명시적으로 허용한다. 외부 역할을 모르는 이전 서버에서도 새 계정이 전역 자료를 읽을 수 없어야 한다.
- DB 이전은 기존 계정·암호 해시·수납·감사·접수·기기 자료를 보존한다. 사용자 자료 DB를 직접 열거나 이전하지 않으며 임시 DB로 검증한다.

## PC 화면

- 메뉴에 **동별 관리**를 둔다. DONG 계정의 기본 화면이며 기존 전체 계정도 같은 화면을 사용할 수 있다.
- 기준일·동 선택·검색 다음에 동별 현황 표와 처리할 접수 목록을 보여준다. 접수 등록·노선 계산·배정 확정은 구분한다.
- 지표는 선택일 예정·완료·미배정·재방문과 전체 기간의 지난 미처리·예정일 없음을 구분해 표시한다.
- 동 행이나 지표를 누르면 해당 범위의 접수 목록으로 이어진다. 선택한 동·날짜·검색·페이지와 양식 초안을 보존한다.
- 새 접수와 수정은 기존 품목 선택 도구·수수료 규칙을 사용한다. 동은 명시적으로 선택하며 서버가 권한을 검사한다.
- 초안은 계정과 원래 동에 묶는다. 계정이 바뀌면 이전 담당자의 초안을 보여주지 않는다. 변경된 범위의 늦은 응답은 표시하지 않는다.
- 전체 계정의 기존 상세 업무 화면은 유지한다. DONG 계정에는 사용할 수 없는 전역 작업 링크를 노출하지 않는다.
- 사용자 관리에서 DONG 역할을 선택할 때 담당 동을 여러 개 지정하고 이후 변경할 수 있다. 전체 범위/지정 범위를 명확히 표시한다.
- 1440px·980px·좁은 화면, 큰 글씨·어두운 테마에서 주 동작·오류·재시도가 가려지지 않아야 한다.

## 전용 API 계약

prefix는 `/api/dong-work`이다. 조회 역할은 ADMIN/INTAKE/LEAD/DONG, 변경 역할은 ADMIN/INTAKE/DONG이다.

- `GET dong-work?date=YYYY-MM-DD&dong=all|<id>|-`: `{date, selected_dong, scope:{mode,dong_ids}, dongs, crews, summary, rows}`. `-`(동 미지정)은 전체 계정만 선택한다. DONG의 `all`은 담당 동 전체다.
- `dongs`: `{id,name,active,crew_id,crew_name,weekdays,daily_limit,daily_limit_m3}`. `crews`는 배정에 필요한 id·name·active·용량·근무 정보만 제공한다. 기기 비밀·주민 자료는 포함하지 않는다.
- `summary`와 동별 `rows`: `scheduled,done,unassigned,revisit,overdue,no_date`를 사용한다. `rows`에는 `id,name`과 위 지표를 둔다.
- `GET dong-work/requests?date=&dong=&bucket=day|done|unassigned|overdue|no_date|revisit&q=&page=`: 기존 접수 쪽 응답의 `rows,total,page,pages` 계약. 최대 50개씩이며 현재 허용된 접수만 조회한다. 완료 지표는 완료 목록만 연다.
- `GET dong-work/requests/{id}`: 허용 접수의 기존 상세 응답. 다른 동 접수는 원문 없이 거부한다.
- `POST dong-work/requests`: 기존 접수 payload + `dong_id`. 현재 허용된 활성 동을 서버에서 이름으로 변환한다. client_req_id 멱등 계약을 유지한다.
- `POST dong-work/requests/{id}`: 기존 수정 payload + `dong_id,req_ver,reason`. 기존 대상과 이동할 동 모두 현재 권한 안이어야 한다.
- `POST dong-work/requests/{id}/cancel`: 기존 취소 payload·req_ver·사유 계약.
- `GET dong-work/assignments?date=&dong=`: 선택 범위의 현재 배정만. 다른 동 접수 원문·ID를 노출하지 않고 공유 배정 여부만 알려준다.
- `POST dong-work/route`: `{date,dong,crew_ids}`. 선택 범위의 해당 예정일 접수만 계산한다. 기존 경로 결과 모양과 `basis:{date,dong,crew_versions}`를 반환한다.
- `POST dong-work/assign`: `{date,dong,plan,basis}`. 현재 범위·예정일·계정·기존 배정 버전을 다시 확인한다. 범위 변경/버전 충돌은 무변경으로 거부한다.
- `GET dong-work/summary.csv?date=&dong=`: 동일 범위의 동별 집계. 주민명·연락처·주소를 포함하지 않는다.
- 사용자 생성에 선택 `dong_ids`를 추가한다. 새 `POST users/{id}/dongs`는 ADMIN만 담당 동을 변경하며 변경 이력을 남긴다.

## 배정 경계

- 선택일 외 접수를 임의로 다른 날 배정하지 않는다. 날짜 변경은 접수 수정으로 먼저 처리한다.
- 기존 수거팀 배정에 선택 범위 밖의 접수가 있으면 그 팀의 배정을 이 화면에서 통째로 교체하지 않는다. 전체 업무 담당자에게 조정을 안내한다. 다른 동의 방문·순서·ETA·배정 버전은 조용히 변경하면 안 된다.
- 노선 계산만으로 확정하지 않는다. 계산 뒤 날짜·동·팀·화면이 바뀌면 옛 결과를 확정하지 못한다.
- 서버는 반영 잠금 안에서 최신 계정과 담당 범위를 다시 읽는다. 준비·계산 중 범위가 취소된 요청은 저장하지 않는다.

## 파일 소유와 구현 순서

### Backend

- `pc/dgpc/users.py`, `store.py`, 새 `dong_work.py`, `server.py`의 동별 업무 라우트·인증 연결, 필요한 `area.py`의 연결된 동 삭제 보호.
- 새 `tests/test_dong_work.py`: 계정/이전/상세/목록/등록/수정/취소/배정/집계/내보내기/권한 변경과 직접 전역 API 우회 검사.
- 기존 전역 서비스·API를 광범위하게 변경하지 않는다. 새 역할이 사용할 수 있는 경로는 명시적인 허용 목록으로 검증한다.

### Frontend

- 새 `pc/ui/screens/dongs.js`, `pc/ui/pc.js`, `pc/ui/screens/users.js`, `pc/ui/pc.css`의 `.dong-workspace` 범위와 필요한 아이콘만.
- 공유 `core.js`를 바꿔야 하면 root와 소유를 맞춘다. 기존 dispatch·모바일 intake 수정은 동결한다.
- 새 `tests/test_dong_work_ui.py`: 실제 모듈·가상 API의 UI 경합/초안/정상 흐름과 실제 임시 API 연결 흐름을 구분해 기록한다.

### Root 통합

- API 계약의 사양 검토와 교차 동 데이터 읽기·쓰기·출력 우회를 독립 검토한다.
- 새 역할의 전역 API·raw print·작업/파일 경로 차단 행렬을 확인한다. 사용자 변경/재로그인 뒤 이전 동 초안·화면이 남지 않아야 한다.
- npm·CI 연결, 생성 문서·버전, 전체 시험, 원격 OS 시험과 실제 Windows 배포본을 검증한다.
- 사용자 지정 동·실제 주민 자료 없이 가상 동 A/B/C와 전체/단일/복수/빈 범위 계정으로 검증한다.

## 구현 검토 기록

- Backend 실제 SQLCipher·HTTP 23개와 기존 세션 취소 19개 통과. v7→v8 보존·되돌림, 전역 API·raw 출력 차단, 복수·빈 범위, 경합·멱등·공유 배정 무변경을 포함한다.
- 독립 보안 검토에서 권한 검사와 상세·목록 조립 사이 동 이관/권한 변경의 읽기 경합을 재현했다. 전용 조회와 bootstrap/me를 짧은 동일 잠금으로 묶고 응답 전송은 밖에서 처리한다. 전역 예약량 경고는 동 담당자 응답에서 제거해 담당 동 기준으로 다시 계산한다. 독립 focused 9개와 proof 변조·동일 동 다른 계정·중복/타동 배정·정상 멱등 7시나리오를 통과했다.
- UI 검토에서는 완료 지표 목록 구분, 모달 하단 동작 고정, 품목 Enter 추가, 기존 저장 단가/확인 대기 표시, 목적 동 중복 조회, 취소 사유 전달, 인증 취소 시 민감 양식 초기화를 보완했다. 동일 계정으로 재인증해 계속하면 기존 초안을 보존한다.
- root 실제 브라우저 흐름은 첫 비밀번호 변경 → 복수 동 조회 → 위치 포함 신규 접수 → 계산/명시 배정 → 기타 사유 취소 → 담당 동 회수 후 조회 거부 → 관리자 전체 동 표시를 확인했다. 실제 배포 EXE에서도 같은 흐름을 실행하는 `tests/test_dong_work_bundle.py`를 추가했다.
- 이전 서버가 정상 자산을 제공해도 새 기능이 적용되지 않는 재사용 문제를 재현했다. `state` 본문을 유지하고 `X-DG-Version`을 확인하며 GUI/CMD 모두 버전 없음·불일치를 거부한다. 기존 서버를 종료하거나 새 DB를 만들지 않는다. 정상 버전의 기존 pc.js HTML 진입은 계속 지원한다. GUI 실행 앱 56확인·CMD 43확인과 PowerShell BOM·구문 검사가 통과했다.

위 기록은 구분된 검토·회귀 증거다. 전체 게이트·원격 OS·현재 배포 EXE 결과는 통합 실행에서 따로 확인한다. 기관 보고서 서식 조정은 사용자 요청대로 보류한다.
